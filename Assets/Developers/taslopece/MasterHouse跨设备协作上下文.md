# MasterHouse 跨设备协作上下文

> 用途：将本文件与 `Assets/Developers/taslopece/` 一并同步到其他开发设备，作为进入项目时的快速上下文与协作约束。
>
> 更新日期：2026-08-12。本文可独立阅读，不依赖任何设备本地的绝对路径或外部文档；如某台设备另有完整设计／技术资料，以该设备已同步的最新版为准。

## 1. 项目定位与协作方式

- 项目暂名：`The Guesthouse of Meros`；新人培训期的可玩 Demo。
- 类型：温情叙事 RPG + 生活模拟经营；淡水彩绘本、低饱和、动物拟人。
- 核心命题是「活人感」：主角因视觉／人面识别障碍将旅客看作动物，在经营和理解具体的人中完成自我和解。不得把该障碍或结局反转仅作为噱头。
- 将策划体验放在讨论顺序的首位：设计目的与玩家体验 → 核心规则和内容节奏 → Demo 范围 → 技术实现与成本。
- 主动指出体验风险、规则冲突、实现成本与范围问题；有限周期内优先交付少量完整闭环。探索想法不是既定规则，确认后才写入稳定结论。

## 2. 核心体验与 Demo 边界

核心循环：接待客人、理解其显性和隐性需求 → 在节点画布规划生产管线 → 产出家具／装饰／服务所需物资 → 布置民宿空间回应需求 → 获得反馈、推进叙事并解锁下一位客人与生产能力。

- 局内是轻量、可成长的 `Masterplan` 式节点生产与布线；强调空间、配方、分流、供需和效率选择，避免高压生存、限时失败与重度精算。
- 局外是温馨的民宿经营和空间布置，必须与局内产出和客人反馈形成双向关系，不能割裂成独立小游戏或单向材料交付。
- Demo 优先保证核心房间、约 3 名客人、基础资源节点，以及「玩法—叙事—情绪」完整闭环；不为 P2 的抽卡、社交等尚未确认系统预建架构。

## 3. 设计结构与原则

### 局内

- 层级：`House → 房间（大关）→ 设备／设备组合（小关）→ 节点画布`。Demo 只投放一个 House；房间不要求无缝缩放地图。
- 画布由可配置 Grid 组成；节点可占多格，连线也逐格占位。任何占格判断必须逐格查询，不能假定形状永远是矩形。
- 连接创建时可一次性 A* 给出合法路径；之后允许玩家手动理线。棋盘变化使连线非法时断线、停止传输，不自动修复。
- 节点类型：资源、加工、仓库、中转。中转节点通过配对 Pin 实现转向／分流；不同连线不能共格或穿过节点。
- 目标没有「完全玩完」的单一概念；任务面板表达目标，玩家可以用不同方案达成。Goals 的具体结算仍未定案，代码只留占位。

### 局外

- House 层级：`House → 房间 → 设备（可玩）／装饰物（不可玩）`。
- 经济：货币来自服务，用于购买设备／装饰；声望来自完成服务，拒绝或未完成会扣除，也是解锁门槛；装饰分来自房间、设备和装饰，当前主要是展示值。
- 访客可并列出现在场景，含一般与特殊访客。单客人有到来、等候、成功服务、拒绝／失败等状态；需求由展示、任务条件、奖励／惩罚构成。
- 对话系统确认自研，功能规格已定案：由单句、事件、分支组成对话组，按种族和触发分类入池；对话事件可驱动访客业务状态。

## 4. 工程架构硬约束

- 采用 MVVM：Def／ScriptableObject 是运行时只读 Model；运行时状态为 Data；只有 Manager 可改 Data；View 只读并表现；Controller 只将输入翻译为 Manager 命令。
- 逻辑层使用固定、确定性的 tick。禁止 `Time.deltaTime`、`DateTime.Now`、无种子随机；速率和时长均以 tick 表示。表现层可插值或随机，但不得回写业务状态。
- 每 tick 固定顺序：**投递 → 节点逻辑 → 取货**。竞争按优先级分层、同优先级轮询；遍历必须按稳定 ID／坐标排序，不能依赖 `Dictionary` 或 `HashSet` 枚举顺序。
- 链接保存玩家手工调整后的折线路径、稳定 LinkId、持货槽、节拍与在途计时；除「Pin 类型不兼容时有意清空」外，物资守恒。背压通过链接持货自然传回上游。
- 非法临时态仅冻结本次移动对象；其他合法对象继续模拟。存在任何非法态对象时拒绝存档。
- 局内外共用一次游玩进度；目标为 `persistentDataPath` 下的 JSON，禁止 PlayerPrefs。设置独立于游戏存档。当前重写期局外存档暂时移除，仅保留统一存档接缝。

## 5. 模块与局外重构现状

- 目录按功能模块划分，不用「OutGame／局外」这类位置名；只有局内外共同依赖的能力进入 `Core`。局内模拟保持为强内聚的 `NodeSim` 模块。
- 局外重写中，旧 `OutGameUI` 等旧逻辑冻结只读：新模块每验收一个，再删除对应旧代码；不要一边重写一边改旧架构。
- Prefab 是布局的唯一真相源：保留手调 Prefab、`OutGame*View` 引用容器和纯表现组件；禁止代码 Build 兜底与 Bind/Build 双路线。动态内容使用 Prefab 模板实例化。
- 内容数据（访客、房间、设备、图鉴、台词、任务等）必须进入强类型 Def／SO；手调数值／文案改资产，AI 新增内容也加资产，不新增管道分隔字符串等弱类型数据。
- 家具模块本轮保留；只处理与旧 UI 的依赖切断和配置 Def 化。内部 MVVM 化、锚点数学合并、多房间玩法留待二轮设计。

当前局外重构进度：阶段三模块重写已完成，旧 `OutGameUI` 上帝类、代码布局兜底和 PlayerPrefs 旧存档均已退役；当前由 `HouseClock`、`Economy`、`Visitor`、`Codex`、`Dialogue`、`HouseUI`、`Furniture` 七个模块承载。统一存档与完整对话系统仍待后续实现。

### 访客系统的现行模型

- 访客由「种族模板 → 日程表」生成运行时实例，不再是 4 个固定角色。日程明确配置第几天、出现时刻与种族，零随机投放、零同时人数上限。
- 生命周期为：前台等待接待 → 服务中 → 提交评分 → 闲逛 → 离场；前台等搭话与服务中等交货分别超时，均按拒绝处理。
- 需求与物品以可继承的 `TagDef` 森林匹配；物品仅需标最细叶子标签。需求 roll 使用由运行种子、日程日和日程下标派生的确定性随机，不能用 Unity 全局随机。
- 一次提交即结算且不可补交；满意度为不对味／一般／满意／完美。到打烊时，一切 tick 业务冻结；处理完仍在等待的访客后，玩家可结束今天并进入日结。

### 对话系统的现行设计

- 对话由 `DialogueManager` 管理；对话组由单句、业务事件和带条件的分支构成。事件／条件以 `[SerializeReference]` 多态配置，分支只允许继续本组、跳另一组或结束。
- 模态对话期间须以“原因集合”关闭营业闸门，避免恢复时错误解除打烊等其他闸门；场景气泡不关闭闸门。
- 对话事件只做一次性状态转换或结算；离场等必发后续只能由访客状态机在 tick 内推进，不能依赖对话播完，防止 ESC 中断造成卡死。
- 旧 `DialogueOverlay`／旧对话 Prefab 和单方法台词接缝属于退役目标；新纯对话框与交付页面仍待实现。交付预览需要只读试算满意度接口。

### 家具配置导表

- 家具与房间配置以 Excel 为唯一数据源：导出 CSV 后由 Unity 自动整表重建对应 ScriptableObject。不要直接在 Inspector 手改这些表资产，否则下次导表会覆盖。
- 表格第一行是中文列名、第二行是字段名参考；行序就是商店／收纳等展示顺序。图片可使用 Resources 相对路径或 `Assets/` 完整路径。

- 本文件已包含跨设备开始协作所需的稳定规则；即使没有其他项目文档，也可以据此讨论设计、审阅改动或继续实现。

- 代码、配置和资产仅表示该设备当前已实现的状态，不自动等同于最终策划定案。
