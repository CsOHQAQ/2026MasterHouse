## 1. 游戏概述

经营模拟游戏「MasterHouse」。玩家经营一栋房子（局外）：接待访客、满足他们的需求、赚货币与声望、买家具装修房间。

游戏分两侧：

| 侧 | 内容 | 时间 |
|---|---|---|
| **局外（House 经营）** | 时钟与日程、访客生命周期、需求与结算、家具摆放与装饰分、商城、对话 | 全局固定 tick（§16.4） |
| **局内（小游戏）** | 访客的「小游戏类需求」调起的一局 UI 小游戏，唯一出口是一个 0~100 的分数 | **自治**，与全局 tick 无关（§3.1） |

> **重要沿革（2026-08-14）**：原设计的局内是一套对标 Masterplan Tycoon 的**节点产线模拟**（资源/加工/仓库/中转节点 + 物资运输 + 背压 + 后台稳态结算）。该玩法**已全线废弃**，轻量化重构为小游戏。
> 物资（`ItemDef`）、配方、仓库节点、加工节点、`PlayerCargo`、tick 三阶段流水线整条链已从工程中删除。
> 唯一被继承下来的是**网格与描格连线**这套空间玩法资产（§4、§5），它现在服务于第一个小游戏「修理电路」。

**空间布局优化仍是小游戏的核心**：画布有限、节点占格、导线也占格，玩家要在有限空间和有限导线预算里把电送到尽可能多的电池上。

## 2. 总体架构：MVVM 分层

| 层 | 职责 | 规则 |
|---|---|---|
| **Model** | 策划配置的静态数据（各类 Def，ScriptableObject） | 运行时**只读** |
| **ViewModel／数据类** | 运行时状态（NodeData、LinkData 等） | 只能由 Manager 修改；可被 View 读取/订阅 |
| **ViewModel／Manager 类** | 纯逻辑运算（GameManager、各局外 Manager；小游戏内的 LevelManager / LinkManager / CircuitSolver） | 持有并推进数据类；Manager 间通信经 GameManager |
| **View** | 表现层（局外各 `*View` 字段袋与页面绑定；修理电路的 `CircuitBoard` UGUI 渲染） | 由 ViewModel 生成，绑定对应数据类；**只读不写**，写操作必须经 Manager |
| **Controller** | 玩家输入（点击、拖拽、描格、放置） | 把输入翻译成对 Manager 的调用 |

数据流向：`Def（策划配置） → Data（运行时初始化） → Manager（推进/求解） → View（表现）`。

### 2.1 View 数据感知【已定稿】

划分原则一句话：**tick 产生的连续变化，View 每帧轮询；玩家操作产生的离散变化，Manager 广播。**

- **连续量**（时钟推进、访客倒计时、状态配色等）：View 每帧读取创建时注入的数据对象，插值渲染。这与 §3.1 配套——逻辑仅 10 tick/秒，连续感必须以渲染帧率采样补间，事件通知对这类需求毫无意义。**不引入字段级事件/响应式绑定**（数据类会长出行为、一 tick 多次变化需去抖、读档后订阅关系需重建，复杂度换不来任何收益）。
- **结构变化**（节点/导线的增删、节点移动、页面进出）：全部由玩家操作触发、不在 tick 内。Manager 在完成修改后广播**粗粒度通知**（携带数据对象引用），View 响应生成/销毁/重建表现物。
- **全量重建是真相源**：读档、开局建关时 View 一律从纯数据全量重建表现；广播只是运行中的增量优化，不是表现的唯一来源。
- 时序推论：单线程下 tick 在一帧内完整执行，View 每帧读到的必然是"完整 tick 之后"的一致快照，不存在半截状态；唯一约定是同帧内**逻辑更新先于表现更新**。
- **修理电路的特例**：它没有连续量——供电是纯函数一次求解（§6.2），所以布局一改就重算加广播，View 不做任何逐帧轮询。`LevelManager`/`LinkManager` 的每个改动布局的公开方法都在收尾时**先 `Solve` 再广播**，订阅方读到的一定是算好的结果。

## 3. 时间模型【已定稿】

### 3.1 固定 tick 推进

- **业务逻辑层以固定步长的确定性 tick 推进**（频率具体数值见待定 #5，暂按 10 tick/秒设计）。当前唯一的 tick 消费者是局外（时钟、访客状态机、日结），驱动方是 `GameManager` 的全局心跳（§16.4）。
- **所有速率配置一律以 tick 为单位**（"每 N tick 一次"）。
- **逻辑层（ViewModel 全部代码）禁止出现 `Time.deltaTime` / `DateTime.Now` / 无种子随机**。连续感全部由 View 层插值实现。
- 动机：固定 tick + 固定处理顺序，使存档读档后可精确复现。

**小游戏是明示的豁免区**：小游戏自己把 `deltaTime` 折算成自己的步长（需要的话），与全局 tick 零关系。理由有二——小游戏期间营业闸门是关的，跟着全局心跳走会被一起冻住；而且自治才能兑现「小游戏与其他模块零耦合」（依赖方向见 §8.5）。小游戏内允许 `Time.deltaTime`、允许无种子 `Random`：它的结果由玩家操作决定，不是确定性业务推演。**唯一的例外是关卡抽取**，那个必须确定性（§8.4）。

> 修理电路实际上一拍都不需要：供电判定是纯函数，玩家每次改动后重算一次即可（§6.2）。自治时间是框架能力，不是每个小游戏都得用。

### 3.2 tick 三阶段流水线【已退役 2026-08-14】

> 原为「投递 → 节点 → 取货」的物资运输流水线。随节点产线玩法废弃**整体删除**，代码里已无对应实现（`LevelManager` 不再有任何 tick 入口）。
> 小游戏没有流水线：供电是一次性纯函数求解（§6.2）。局外业务的 tick 是单阶段的，见 §16.4。

### 3.3 tick 内竞争仲裁【已退役 2026-08-14】

> 原为多条链接争抢同一 Pin 时的「优先级分层 + 同级轮询」。**前提已消失**：现在一个 Pin 至多接一条线（§6.1），不存在争抢，`Priority` 与轮询指针字段已删除。
> §11.2「禁止依赖 Dictionary/HashSet 枚举顺序、一切遍历按稳定键排序」这条**仍然全局有效**，并未随本节退役。

### 3.4 未打开的关卡：完全不推进【已退役 2026-08-14】

> 原为「关卡数据常驻内存、只推进玩家打开的那一个」。随「关卡即家具」废弃而**整体失效**：小游戏关卡不常驻、不存档，每次打开由 `LevelManager.BuildLevel` 重新造一份，放弃即销毁、再进重置（§8.4）。
> 由本节废掉的待定 #7（后台稳态结算算法）维持作废。

## 4. 网格与空间模型

### 4.1 基础结构

- **Grid（单元格）**：Model 层的最小单位，仅含相对坐标（DeltaPosition）与格子类型。**不含任何运行时状态**（占用与否属于运行时数据，归 ViewModel 的占用索引管，见 §10）。
- **GridGroup**：一组 Grid，承担形状描述与基础查询/碰撞判定。节点占格形状、画布形状都用它表达。
- 节点形状可以是非规则的——一切占格判定必须走 GridGroup 逐格查询，**不得假设矩形**。
- 画布（原方案中的 CanvasDef）**取消独立类，内联进 LevelDef**（见 §8）。

### 4.2 占格与合法性规则【已定稿】

> **本节是从节点玩法完整继承下来的资产，一行未改**，现服务于修理电路。

- 节点占据其 GridGroup 覆盖的格子；**导线同样占据其途径的每一个格子**。
- 合法性检查：导线的每个途径格 必须 ∈ 画布 ∧ ∉ 任何节点占格 ∧ ∉ 其他导线的途径格。
- **导线之间一律不允许共格；导线不可进入任何节点（含中转件）的占格**，只能接到节点的 Pin 上。
- 推论：两条线在空间上"交叉"，唯一途径是走中转件的一个分组进、对面 Pin 出（"立交"由分组机制实现，不是空间穿越，见 §6.3）。**十字件唯一的用途就是这个**。

### 4.3 非法临时态【已退役 2026-08-14】

> 原设计：移动节点造成冲突时冻结被移动对象、并禁止存档。这套机制是为「有存档的产线」设计的。
> **小游戏无存档、且摆件有幽灵预览绿/红**，落点非法时 `LevelManager.MoveNode` 直接返回 false 什么都不做，没有中间态可言。
> `NodeData.IsIllegal` / `LevelData.HasIllegalObjects` 两个字段已删除；由本节引出的待定 #14（非法态 UI 与存档拦截）随之作废。

## 5. 布线系统【玩家手动描格】

> 本节与 §4.2 同为从节点玩法完整继承的资产。`LinkManager.ValidatePlayerPath` **一行未改**地搬了过来——
> 这是整次迁移最值钱、也最容易写错的一块，改动它前请先想清楚。

- 导线形态：**格子内的直线 + 直角折线**（4 方向）。
- **创建时**：玩家从 Pin 按下起**描格**——路径跟着鼠标经过的格子逐格延伸，松手时必须落在合法目标 Pin 的接口格上，否则本次绘制作废（不留半截线）。手感细则：
  - 鼠标落回已描过的格 → 截断到那一格（可一次退多格）；
  - 斜向移动 → 自动补一格（优先沿上一段方向先走再转弯，拐角更少）；
  - 撞到非法格（越界/被占用/与自身重叠）→ **停住不延伸、不作废**，玩家绕开继续描；
  - **导线预算耗尽同样是"停住不延伸"**（§8.3），与撞墙一个手感——本次绘制不作废，玩家可以退回重画。
- **终点判定**：优先取鼠标命中的 Pin，没命中则按路径末端反查 Pin——玩家把线画到接口格上就算连到，不必再精确悬停在 Pin 标记上。
- **路径合法性一律在 Manager 层复核**（`ValidatePlayerPath`）：不信任 Controller 传入的路径——每格 ∈ 画布 ∧ 未被占用、4 向连续、整条不自交、首尾接在两端 Pin 的接口格上；玩家从输入侧往输出侧画时整条反转后存储（`PathCells` 一律 from→to）。
- 建线时另有两道拦截（§6 新增）：**目标 Pin 已被占用**（一 Pin 一线）、**会形成回路**（`CircuitSolver.WouldCreateCycle`）。
- **A\* 自动布线已删除**：`FindPath` 的唯一调用方是随本轮退役的调试面板，正式玩法从来不用它。
- **删线**：右键短击导线即删（高频操作，免选中），预算随即退还。移动或删除中转件时，**附着的导线直接删除并退还预算**——不保留断线态，小游戏可无限重画，留个半死不活的对象不划算。
- **理线**（抓住已有线段拖排走线）：**仍未实现**。描格代码就位后它是纯增量，留待后续。
- `LinkData.PathCells` 存储**玩家著作的折线**（`List<Vector2Int>` 途径格）；小游戏不存档，故不涉及序列化。

## 6. Pin 与导线：电量模型

> **2026-08-14 整片改写。**原「物资运输 + 速率 + 节拍 + 在途 + 背压」模型随节点玩法废弃。
> 现行模型是**电量制、无时间维度**：一次纯函数求解算完全场，没有"在途""阻塞""守恒"可言。

### 6.1 Pin 模型【已定稿】

Pin 是节点上的接线口。**PinDef 字段只剩三个**：

| 字段 | 说明 |
|---|---|
| `MaxRate` | 本 Pin 送出多少电。**仅电源的输出 Pin 有效**——中转件一律不限流，其输出量由分组公式算出 |
| `Direction` | `None` / `Input` / `Output`。电源固定 Output、电池固定 Input、分流合流由策划配死；十字件留 `None`，运行时随第一条接上的线确定（`PinData.RuntimeDirection`） |
| `PinGroup` | **中转件分组号**，-1 = 不属于任何分组（不导电）。件型完全由分组与方向决定，见 §6.3 |

- **Pin 自身没有位置概念**；Pin 在节点上的位置（哪个格 `LocalCell`、朝向哪边 `Facing`）由所在节点的 `PinLayout` 记录，策划手摆。
- **一个 Pin 至多接一条线**（`PinData.Link`，null = 空口）。这条由 `LinkManager` 在建线时拦截，**不是靠约定**。因此不存在多线争抢，§3.3 的仲裁机制随之退役。
- 链接本身**没有载量上限**——"这个口通多少电"是 Pin 的属性，不是靠"接几条线"表达（后者是被推翻的份额制模型）。
- **分组号与 Pin 下标完全解耦**（不再是旧版"互指的配对索引"），所以删一个 Pin 不必连带删伙伴、也不用重映射任何索引。

### 6.2 电量模型与求解【已定稿】

三条规则就是全部：

1. **电源**按每个输出 Pin 各自的 `MaxRate` 送出电量；总供电 = 各输出 Pin 的 `MaxRate` 之和，没有独立的"总闸"字段。
2. **中转件**按分组换算，公式只有一条（§6.3）。
3. **电池**收到的电量 = 各输入 Pin 上链接携带电量之和，再逐条判定：
   - 收到量 `== RequiredAmount` → 点亮；
   - 收到量 `< RequiredAmount` → 不亮；
   - 收到量 `> RequiredAmount` → 看 `AllowExcess`，允许则点亮，否则**不亮**。

   `AllowExcess = false` 是核心难度旋钮：玩法从"尽量多连"变成"**精确分配**"。多输入口意味着电池自己就能合流，**合流器不是通关必需品**，而是省导线格数的优化件。

**判定是纯函数**（`CircuitSolver`，无状态）：从各电源沿链接**记忆化传播**电量 → 汇总各电池收到的电量 → 逐个判定。玩家每次增删线/摆件后重算一次，**不需要 tick、不需要动画时序**。求解结果写回 `LinkData.Power`、`NodeData.ReceivedPower`/`IsLit` 与 `PinData.OutPower`（后者是每轮清零的记忆化缓存，除求解器外任何人不得写入）。

**成环在建线时拒绝**（`LinkManager.TryCreateLink` → `CircuitSolver.WouldCreateCycle`）：合流器输出绕回自己的输入会让"输出 = 输入之和"变成自指方程，纯函数求解器无解。
⚠ **图的顶点是 (节点, 分组) 而不是节点**——十字件的两个分组互不连通，按节点粒度检测会把「两条线各走一组的正常交叉」误判成环，那正好废掉十字件唯一的用途。

### 6.3 中转件与分组【已定稿】

**每个输出口的电量 = floor( 组内输入之和 / 组内输出口总数 )**

三种件型全是这一条公式的特例，**共用同一个 `TransitNodeDef` 类**（空壳），差异全在资产的 Pins 配置里——**加件型 = 加资产，不加代码**（§15.3）：

| 件型 | 组的形状 | 公式结果 | 用途 |
|---|---|---|---|
| **十字件** | 两个组，各 1 进 1 出（方向留 `None`，运行时定向） | `floor(x/1) = x`，直通 | 转向与交叉——线不能共格、不能穿节点，两条线要交叉就只能走它 |
| **分流器** | 一个组，1 进 N 出 | 平分（向下取整） | 把一份电分给多个电池 |
| **合流器** | 一个组，N 进 1 出 | 求和 | 把多路电合成一路，省线 |

- **分母是输出口总数，不是已接线的口数**——没接线的口那一份会浪费掉；整除余数同样蒸发。这给了玩家凑整除数的动机。
- 「同步」方向（`Direction = None`）只在**恰好两个口的组**上成立——三口以上分不清谁是那个"1"，所以分流/合流必须配死进出，编辑器会校验。
- 本轮只做 1:N 与 N:1；组内既多进又多出（M:N）公式照样成立但未验收，编辑器给警告。
- 占格规则与其他节点**完全相同**：导线只能接到其 Pin，不可与其占格重叠。

> 由旧「配对 Pin 类型同步传播」引出的待定 #2 随本节作废——电量没有类型，无从"不兼容"。

### 6.4 物资守恒与背压【已退役 2026-08-14】

## 7. 节点类型规格

`ENodeType` 现为三类（`Processor` / `Storage` 随物资链退役已从枚举中删除）：

| 类型 | 枚举值 | 输入 | 内部行为 | 输出 | 策划可配 |
|---|---|---|---|---|---|
| **电源** | `Resource` | 无 | 无 | 各输出 Pin 按自己的 `MaxRate` 送电 | 占格形状、Pin 布置（各 Pin 的 `MaxRate`）。**只能预置** |
| **中转件** | `Transit` | 组内输入 Pin | 按 §6.3 公式换算 | 组内输出 Pin | 占格形状、Pin 布置（`PinGroup` + `Direction`）。**玩家可摆**，数量上限见 §8.3 |
| **电池** | `Condition` | 各输入 Pin | 求和后按 `Conditions` 逐条判定点亮 | 无 | `Conditions`（`RequiredAmount` + `AllowExcess`）、占格形状、Pin 布置。**只能预置** |

- **电源与电池是关卡预置的题面**：不可移动、不可删除、不可由玩家摆放（`BuildableNodes` 里混进非中转件时编辑器报错）。中转件是玩家唯一能摆的东西。
- 电池的 `Conditions` 保留为**列表**：多条之间「全部满足」才点亮，留空 = 恒点亮（编辑器会警告"等同于白送分"）。实际关卡配一条即可，留列表是给将来扩展留位。
- `ResourceNodeDef.OutputCount` 是份额制时代的遗留字段，**已弃用、`[HideInInspector]`、不参与任何运算**，保留只为让文档与代码可对照。

> 阅读顺序提示：**先看 §8.5（框架契约）再看 §8.1~§8.4（修理电路的关卡）**。编号不重排是为了不打断外部引用（见文首）。

### 8.1 LevelDef：修理电路的一关【已定稿】

`LevelDef : MinigameLevelDef`（ScriptableObject），一关一资产，**类名保留不改**——目录已经在 `Minigame/Circuit/` 下，叫 `LevelDef` 不歧义。字段只剩四个：

| 字段 | 说明 |
|---|---|
| `Canvas` | 画布形状，**内联 GridGroup**（取消独立 CanvasDef 类） |
| `PresetNodes` | 预置节点列表：`(NodeDef, 放置格坐标, 可否移动, 可否删除)`。**电源与电池是题面，靠它预置** |
| `BuildableNodes` | 本关可摆的中转件与各自数量上限 `(NodeDef, MaxCount)`。非中转件混入时编辑器报错 |
| `MaxLinkCells` | 导线总格数上限，0 = 不限 |

### 8.2 全局仓库 PlayerCargo【已退役 2026-08-14】

> `PlayerCargoData` 连同 `ItemDef` / `RecipeDef` / `TagDef` 与 `GameData/Items,Recipes,Tags/` 资产**已整体从工程删除**。
> 产地（产线/家具效果产出）与出口（访客交付）先后消失，它不再有存在理由。待定 #15 随之结案。

### 8.3 两个资源约束【已定稿】

关卡的难度旋钮就是这两个，都在 `LevelDef` 上：

| 约束 | 落点 | 手感 |
|---|---|---|
| **导线总格数上限** | `MaxLinkCells`（0 = 不限） | 口径 = `Σ link.PathCells.Count`（`LevelData.UsedLinkCells`）。描格时预算耗尽即**停住不延伸**，与撞墙同一手感；删线退还预算。描格途中还要额外算上当前正在画的格数 |
| **中转件数量上限** | `BuildableNodes` 的 `MaxCount` | `CanBuild` 按它校验；达上限后件库条目置灰 |

UI 常驻显示 `导线 34/50`、`中转件 2/3`，剩余为 0 时数字变红。

**计分**：

```
分数 = 点亮的电池数 / 电池总数 × 100   （四舍五入，0~100 的 int）
```

- **按节点个数**，不按需求量加权，不给部分分（"点亮"是二元的，与 `AllowExcess` 的二元语义一致）。
- **线长与中转件用量不参与计分**——它们是准入约束，不是评分项。
- 粒度提醒：**2 个电池的关卡只能出 0/50/100 三种分数**，想要细梯度就多放电池。关卡编辑器的校验会把可能的分数列表直接打出来。

### 8.4 一局的生命周期【已定稿：用完即弃】

**小游戏不存档**（无限重开即重置，不需要），所以没有常驻、没有 Open/Close 两层：

- `LevelManager.BuildLevel(def)` → 每局新造一份 `LevelData`（预置节点就位 + 算一次 `Solve`），放弃或完成即销毁。
- 【放弃】/ ESC / 点遮罩 → `onAbort()`，**不结算**，访客保持「服务中」，可再次点开重玩，**局面重置**（不保留上次布线）。
- 【完成】按钮**随时可点**，按当前点亮占比结算 → `onFinish(score)`。没有失败条件，没有时间/步数限制。

**关卡抽取：锁定同一张**

```
关卡 = 池[ Hash(runSeed, 访客实例Id, 需求Id) % 池长度 ]
```

同一位访客反复进出**恒定抽到同一张**——"重开"是磨同一关，而不是刷关卡（否则理性玩家会反复退出直到抽到最好做的那张）。与项目现有的对话组选取是同一套派生种子思路，读档也不刷。**这是 §3.1「小游戏时间自治、允许无种子随机」的唯一例外**：抽取必须确定性，用 `DeterministicRng.Hash`。

### 8.5 小游戏框架【2026-08-14 定稿】

> 落地依据：`Docs/归档/小游戏框架与修理电路说明.md`。

**依赖方向是整个框架的立身之本**：

```
Visitor / Dialogue          ←─ 不认识小游戏
      │ StartMinigameAction（对话分支事件）
      ▼
MinigameOverlay（宿主）     ─→ 认识 IMinigame 与 MinigameDef
      │ Launch(level, onFinish, onAbort)
      ▼
具体小游戏（Circuit…）      ←─ **不认识任何 Manager**
```

具体小游戏**只认识两样东西**：`IMinigame` 接口和自己的关卡类型。它不引用 `GameManager`/`VisitorManager`/`EconomyManager`/`HouseClockManager`/`HouseUIManager`，也不认识 `MinigameOverlay`/`MinigameDef`。**这条是硬约束，改完请对 `Minigame/Circuit/` 全文检索一遍**（唯一明示例外是 `Circuit/Editor/` 的 Prefab 生成器——它是 authoring 工具，整个类在 `UNITY_EDITOR` 内，产物是资产而不是运行时行为）。

**契约**（`Minigame/IMinigame.cs`）：

```csharp
public interface IMinigame
{
    /// level 由宿主抽好；结束时必须调且只调一次 onFinish 或 onAbort。
    void Launch(MinigameLevelDef level, Action<int> onFinish, Action onAbort);
}

/// 各小游戏关卡资产的共同基类（只为给关卡池一个类型约束，无字段）。
public abstract class MinigameLevelDef : ScriptableObject { }
```

`onFinish(score)` 的 score 是 **0~100 的 int**，各小游戏自己定义怎么算。小游戏是 UGUI Prefab，根节点挂实现 `IMinigame` 的 MonoBehaviour。

**MinigameDef**（一个小游戏一资产）：`minigameId` / `displayName` / `prefab`（**强类型 `GameObject` 引用**，不走 Resources 路径字符串）/ `levels`（关卡池）/ 三个分档阈值 `plainMin=1` `satisfiedMin=60` `perfectMin=100`（分数 → `EServeSatisfaction` 四档）。
**难度不做单独抽象**：要区分难度就多做一个 `MinigameDef`（同一个 prefab、不同关卡池）——用资产模拟档位，符合 §15.3。

**宿主 `MinigameOverlay`**（`IHouseOverlay`，压进 `HouseUIManager` 叠加层栈，与 `DialogueOverlay` 同例）：关营业闸门（`EClockStopReason.Minigame`，**计入 `IsWorldFrozen`**）→ 实例化 prefab 取 `IMinigame` → 抽关卡并 `Launch` → 接 `onFinish` 查阈值定档后调 `VisitorManager.CompleteNeed(instanceId, satisfaction)`、接 `onAbort` 只关页面 → 销毁实例、开闸门、退栈。

⚠ **两处退栈顺序的坑**（同一类问题的两面，已写进 `MinigameOverlay` 类注释）：

| 位置 | 坑 | 处置 |
|---|---|---|
| 出口 | `CompleteNeed` 内部会同步压入【完成服务】对话层 | **先弹栈关小游戏页、再调业务**，否则 `PopOverlay` 弹掉的是对话框。两步在同一调用栈内完成，tick 插不进来 |
| 入口 | `StartMinigameAction` 在 `DialogueManager.ChooseOption` 内执行，此时对话层还在栈顶且仍在播 | 事件**只登记意图不当场开页**；真正打开由 `HubPage.OnDialogueEnded` 在 `DialogueOverlay.CloseFromPlaybackEnded()` **之后**调 `MinigameOverlay.ConsumePending`。离开 Hub 页时 `DiscardPending()` 丢弃未消化的请求 |

## 11. 确定性与存档守则（AI 开发硬规则）

任何人（或 agent）在 ViewModel 层写代码时必须遵守：

1. **禁止** `Time.deltaTime`、`DateTime.Now`、无种子的 `Random`。时间只来自 tick 计数。
2. **禁止**依赖 `Dictionary`/`HashSet` 的枚举顺序；一切遍历按稳定键（LinkId、NodeId、格坐标）排序。
3. 所有速率、时长以 **tick** 为单位。
4. **View 层只读**；数据类只能被 Manager 修改。
5. 存档 = 数据类全量序列化；JSON 文件（persistentDataPath），**禁止 `PlayerPrefs`**（待定 #9）。**小游戏整体不入存档**——无限重开即重置（§8.4）。
6. ~~存在非法临时态对象时拒绝存档~~ **已随 §4.3 退役**（非法临时态不再存在）。
7. 遇到待定项（见下）：留占位符 + 注释标注编号，不自行决策。

**明示豁免区**（不受 1、3 约束，但仍受 4 约束）：

| 区域 | 豁免内容 | 理由 |
|---|---|---|
| View 层 | `Time.deltaTime`、无种子随机、DOTween 等 | 表现的连续感必须以渲染帧率采样；**但表现结果不得回写业务状态** |
| 小游戏内部 | 同上，且自治步长与全局 tick 无关（§3.1） | 结果由玩家操作决定，不是确定性业务推演。**唯一例外是关卡抽取**（§8.4），必须用 `DeterministicRng.Hash` |

## 14. 术语表

| 术语 | 含义 |
|---|---|
| tick | 逻辑层固定步长时间单位，一切速率的分母（§3.1）。**小游戏不用它** |
| 描格 | 创建导线的方式：从 Pin 按下，路径跟着鼠标经过的格子逐格延伸（§5） |
| 理线 | 玩家手动拖排**已有**导线走线的操作，空间优化玩法的一部分（**尚未实现**） |
| 接口格 | Pin 朝向的那个相邻格（`NodeData.GetPinPortCell`），导线的端点必须落在这里 |
| 电源 / 中转件 / 电池 | 修理电路的三类节点，枚举分别是 `Resource` / `Transit` / `Condition`（§7） |

## 15. 全工程模块化目录规则【2026-08-08 定稿】

> 来源：局外重构访谈（2026-08-08）确定"目录按功能模块划分"后，规则推广到全工程。
> 执行时机：局外重写开工前完成目录重组。**平移是纯机械操作，必须与逻辑重构分开提交。**

### 15.1 原则

- **目录按功能模块划分，模块名必须表达功能含义**。禁止"OutGame/局外"这类只描述位置属性、不含功能语义的伞形命名。
- 模块内部文件沿用 MVVM 分层后缀表达层次：`*Def`（Model，策划配置、运行时只读）、`*Data`（运行时数据）、`*Manager`（逻辑）、`*View`/`*GO`（表现）。**目录回答"属于哪个功能"，后缀回答"属于哪一层"**。
- **命名空间维持单一 `MasterHouse`**（2026-08-08 决策）：快速开发期允许适度耦合换取速度，模块边界靠目录约定维持；后期需要大规模维护时用 Agent 筛查越界依赖，届时再评估子命名空间 / asmdef 硬隔离。

### 15.2 目标结构

```
Assets/Scripts/
  Core/        全局基础设施：GameManager（全局固定 tick 心跳）、GameConfig、统一存档接缝
  Minigame/    小游戏：框架契约（IMinigame / MinigameLevelDef / MinigameDef）与宿主
               （MinigameOverlay，唯一同时认识业务侧与小游戏侧的类），下辖各具体小游戏：
                 Circuit/  「修理电路」：Data/ Runtime/ View/ Editor/
                 Testing/  局内独立测试场景的 Bootstrap 与场景生成器（不进正式流程）
  Visitor/     访客：配置、到访/服务状态、业务结算、表现（局外）
  Economy/     经济：货币/声望/装饰分（局外）
  HouseClock/  游戏时钟与时段划分（局外）
  Codex/       图鉴资料：设备/档案/世界观/成就/日记（局外）
  Dialogue/    对话接缝（局外，占位模块）
  HouseUI/     局外界面壳：Canvas 生命周期、页面路由、各页面绑定
  Furniture/   家具摆放（局外，现有目录保留）
```

### 15.3 Core 准入标准

**只有多方都依赖的东西才进 Core**。单侧使用的工具跟随所属模块：`HouseGmConsole`（局外 GM 面板）→ Economy。当前 Core 只收三样：GameManager、GameConfig、统一存档接缝。将来出现真正通用的框架（如 GM 命令注册机制）再上移——**不预设抽象、不建没有调用方的接缝**。

> 这条在本轮被反复援引：中转件的三种件型共用一个空壳类（加件型 = 加资产，§6.3）、小游戏难度靠多做一个 `MinigameDef` 而不是加难度字段（§8.5），都是同一条原则的应用。

### 15.4 单个小游戏为何不细拆

一个小游戏是强内聚的系统：占格判定、路径校验、求解、渲染彼此咬合，硬拆成 Node/Link/Grid 多模块只会得到形式上的边界与密集的跨模块引用。故**一个小游戏一个目录**（`Minigame/Circuit/`），内部按 MVVM 分 Data/Runtime/View/Editor。

真正的模块边界在**小游戏与外界之间**，由 §8.5 的依赖方向硬约束保证：具体小游戏不认识任何 Manager，唯一的桥是宿主 `MinigameOverlay`。

### 16.4 时间模型：并入全局固定 tick【已定稿】

- 局外业务逻辑（时钟推进、时段划分、访客到访/服务窗口判定、周结算）由 **GameManager 的全局固定 tick** 驱动，遵守 §11 全部硬规则。两套时间轴合并为一套。
- 体验节奏沿用"现实 1 秒 = 游戏 1 分钟"，但以 tick 表达（10 tick/秒 → 每 tick = 0.1 游戏分钟），倍率写入 GameConfig 可配字段（待定 #18），禁止散落魔数。
- 时段与到访判定用 tick / 游戏分钟的**整数比较**，禁止 float 小时累加（旧实现的浮点误差不可复现）。
- **表现层豁免**：游走、气泡、错峰入场动画等纯表现留在 View 层，允许无种子随机与 deltaTime；但**表现结果不得回写业务状态**（旧版访客状态机结果回写业务是反例）。
- **打烊闸门【2026-08-10 定，2026-08-11 已实现】**：游戏时钟到达当日最晚时刻（打烊）后，**一切 tick 业务统一冻结**——局外时钟停止推进、访客的各类倒计时同步停表。
  - 冻结的只是 tick 业务；局外面板操作等玩家交互不在 tick 内（§2.1），照常可用。
  - 解冻由玩家的【结束今天】显式触发：场上尚有未处理访客时该操作不可用，玩家须逐个处理（完成服务或拒绝）；确认后进入当日结算并跳次日开门时刻。
  - 营业时段（开门/打烊时刻）配置于 `VisitorTuningConfig`；打烊是**时间的纯函数派生**（`IsClosedForToday`），不入闸门原因集合。
  - **原动机已消失但结论保留**：这条当初是为了堵死"把局内产线挂机无限刷资源"。产线没了、小游戏也不产出资源，但"一天有界"对访客投放与日结仍然成立。原落点 `LevelManager.TickAll()` 已随三阶段流水线删除。

### 16.5 存档：统一存档（待定 #9 已定方向）

- 局内局外同属一次游玩进度，**共用同一份存档**；JSON 文件（persistentDataPath），**禁止 PlayerPrefs**。
- 重写版**先移除局外存档功能**：标题页"继续游戏/读取存档"临时占位（对"功能等价"的明示豁免），只留统一存档接缝；待定 #9 数据结构定案后接入。
- 设置项（音量/窗口模式）不属于游玩进度，独立为全局配置文件（旧版把设置塞进存档槽是反例）。

### 16.6 数据全部 Def 化

- 访客、房间、设备、台词、任务、成就、日记、面板文案等内容数据全部进 Def（SO），遵守 Model 层"运行时只读"。
- **只为已有内容建 Def**，不为策划案 P2 系统（抽卡/社交等）预建结构。
- 手调数值/文案 = 改资产不碰代码；AI 加内容 = 加资产不改代码。禁止新增管道分隔字符串（`"名字|LV.2|效果|1"`）这类无类型数据。

### 16.9 对话接缝

- 查证结论（2026-08-08）：项目**无对话系统**——无第三方插件，现状只是带 4 句硬编码台词的访客事务面板。
- 对话系统将**自研**，功能要求后续给出（待定 #17）。重写版只做接缝：台词进 Def；"取对话内容、走对话流程"隔离为独立小接口；自研系统进场时替换接口实现，不动访客业务与 UI。
- **功能要求已给出、设计已定稿（2026-08-11）**，完整规格见 `Docs/归档/对话系统设计说明.md`。与 2026-08-08 的预设相比有两处偏差，以新文档为准：①「不动访客业务与 UI」不再成立——对话事件要驱动访客状态（接待/拒绝就是分支选项上的事件）；②接口不再是单方法取台词，`DefDialogueService` 退役，由 `DialogueManager` 取代（`IDialogueService` 接口本身保留为访客侧的解耦接缝，只改返回值形状）。
- **表现层处置修正（2026-08-12，落地前核查）**：设计说明原文写「旧 `DialogueOverlay` 与 `OutGameDialogueView` Prefab 整体退役、新建纯对话框」，该条**已作废**。另一侧的「对话界面 GVN 化」（commit 1206803）造出的正是设计说明 §10 描述的形态（全屏场景 + 左下立绘 + 底部对话条 + 右侧选项列），点名要删的家具快捷栏已删、访客列表已归 GuestRail、需求展示已归任务卡。故 **Prefab 与 `OutGameDialogueView` 字段袋保留并扩展**（改名会断 Prefab 的 `m_Script` 引用），真正退役的只有 `DialogueOverlay` 内那套临时 debug 选项生成逻辑。经核查该 Prefab 与生成器默认布局逐字节一致、无任何手调，故选项列由固定 7 槽改为「模板 Prefab + 运行时实例化」以符合 §16.2 硬约定（无上限、自动排布）。
- 两条跨模块约束在此备案：**模态对话框期间关闭营业闸门**；**对话事件只做一次性状态转换，后续推进一律由访客状态机负责**（对话可被 ESC 中断，不能承担必发动作）。
- **闸门原因集合的落地形状（2026-08-12）**：`HouseClockManager.SetRunning(bool)` 改为原因集合，但需**区分两个派生量**——`IsRunning`（时钟推进与访客业务 tick，原因 = 不在 Hub 页 + 模态对话框 + 打烊）与 `IsWorldFrozen`（局内产线停 tick，原因 = 模态对话框 + 打烊，**不含**页面闸门）。二者必须分开：局内测试场景没有 HubPage，`IsRunning` 恒 false，若局内产线跟着它门控就永不推进（这正是现状只用 `IsClosedForToday` 门控 `LevelManager.TickAll()` 的原因）。打烊仍是时间的纯函数派生、不入集合，真正的持有者只有「页面」与「模态对话框」两个。
- **对话资源重构（2026-08-14）**，现状见 `Docs/对话系统说明.md`（决策与过程记录见 `Docs/归档/对话资源重构说明.md`）。改的是配置形态与编辑方式，接缝形状本身不变（仍是 `IDialogueService` + fire-and-forget），但下面五条与前文的描述冲突，**以本条为准**：
  1. 内容源改为 **Excel/对话表.xlsx**（两页：对话组 / 对话内容）→ CSV → `DialogueTable` **一张整表**。原来的一组一 `DialogueGroupDef`、一族一 `DialoguePoolDef` 与对话编辑器窗口整体退役——Excel 成唯一源之后，散资产的三条理由全部失效，只剩孤儿资产的代价。**只保留校验器**，报错指到 Excel 的 sheet 与行号。
  2. 事件与条件从 `[SerializeReference]` 多态类改为 `DialogueFuncs` 里的**两张函数字典**，Excel 写调用串（`DayAtLeast(3)`），**导入期**解析成 `DialogueCall{func,args}`，运行时零反射。副作用：`[MovedFrom]` 那条「改名 = 静默清空策划数据」的高危约束随之失效。
  3. `IDialogueService` 的触发点参数从「`EVisitorDialogueTrigger` + `EServeSatisfaction` 二维」合并为一维的 **`EDialogueCategory`（八分类）**：初次见面 / 等待接待 / 需求对话 / 需求反馈×4 / 闲聊。「被拒绝」与「服务中交谈」两个分类被吸收进组内分支，不再独立。
  4. 跨组跳转（`BranchOption.next`/`nextGroup`）与 `ExecuteOnInterrupt` 删除；分支选项后面直接跟子句，播完汇合主线下一步。
  5. 访客状态机连带三处：`CanAcceptGuest = HasFreeRoom && !HasAwaitingRoomVisitor`（接待串行化，堵掉「两个人抢一间房」的死锁）；入住后先随机安顿一段才开口示意，**服务超时从示意起算**；只有 `AwaitingRoom` 阻塞【结束今天】，前台访客打烊自动清场。
- **立绘 ID 化（2026-08-14，同日晚些时候）**：表现资源的组织方式改动，逻辑分层不变。缘由是美术要求「更多、且不太好归类的表情差分」——这等于宣告「差分能归类」这个前提不成立，而表情枚举正是建立在那个前提上的。三条与前文冲突，**以本条为准**：
  1. **表情枚举 `EDialogueEmotion` 退役**，`DialogueLine.emotion` 改为 `portraitId`（string）。立绘从 `VisitorRaceDef.portraits`（一列 `平静=路径/高兴=路径` 的双层分隔串，本就违反 §16.6「禁止管道分隔字符串」）搬到独立的 **`Excel/立绘表.xlsx` → `PortraitTable`**：立绘ID → Resources 路径，加差分 = 加一行，不碰代码。`VisitorRaceDef` 只留 `defaultPortraitId`。
  2. **对话表的「种族」列不再接受「通用」与 `/` 多选，一个对话组只属于一个种族**。原因是通用组的多个种族共用同一份 `DialogueLine`：表情是种族无关的键时这没问题（各查各的差分表），换成具体的立绘ID 就成了串脸。代价是内容量随种族数线性增长——这是明知代价后的选择，每个种族本来就该有自己的性格与长相。
  3. **「立绘ID 留空 = 沿用上一句」的承接放在播放期**（`DialogueRuntime.CarriedPortraitId`），不在导表期展开。理由：分支汇合回主线时该顶哪张脸取决于玩家选了哪个选项，静态展不开。这是本次唯一新增的运行时状态，且随播放结束即弃。缺差分回退 + `LogWarning` 那套撤掉，改为**导表期硬校验**（引用的立绘ID 必须存在，否则整表不落盘）。
  连带清理：`stayOvernightPercent` 与种族表的「跨天留宿概率%」列删除（消费方早在同日更早的改动里就没了）。
