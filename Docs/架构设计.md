## 1. 游戏概述

模拟经营游戏，对标 Masterplan Tycoon。玩家在**有限形状的网格画布**上放置各类节点（资源、加工、仓库、中转），并在节点的 Pin 之间拉出**占据格子的连线**来运输物资。**空间布局优化是核心玩法**：画布有限、节点占格、连线也占格，玩家需要通过理线和摆位在有限空间里塞下更高的产能。

游戏由多个**小关（Level）**组成，多个小关可存在于同一场景中；玩家同时只聚焦少数小关，未聚焦的小关在后台以简化方式继续生产。

## 2. 总体架构：MVVM 分层

| 层 | 职责 | 规则 |
|---|---|---|
| **Model** | 策划配置的静态数据（各类 Def，ScriptableObject） | 运行时**只读** |
| **ViewModel／数据类** | 运行时状态（NodeData、LinkData 等） | 只能由 Manager 修改；可被 View 读取/订阅 |
| **ViewModel／Manager 类** | 纯逻辑运算（GameManager、LevelManager、LinkManager） | 持有并推进数据类；Manager 间通信经 GameManager |
| **View** | GameObject 表现层（NodeGO、LinkGO、TransferPulseGO 等） | 由 ViewModel 生成，绑定对应数据类；**只读不写**，写操作必须经 Manager |
| **Controller** | 玩家输入（拖拽、悬浮、Camera 控制、放置） | 把输入翻译成对 Manager 的调用 |

数据流向：`Def（策划配置） → Data（运行时初始化） → Manager（tick 推进） → View（插值表现）`。

### 2.1 View 数据感知【已定稿】

划分原则一句话：**tick 产生的连续变化，View 每帧轮询；玩家操作产生的离散变化，Manager 广播。**

- **连续量**（配方进度、脉冲位置、状态配色等）：View 每帧读取创建时注入的数据对象，插值渲染。这与 §3.1 配套——逻辑仅 10 tick/秒，连续感必须以渲染帧率采样补间，事件通知对这类需求毫无意义。**不引入字段级事件/响应式绑定**（数据类会长出行为、一 tick 多次变化需去抖、读档后订阅关系需重建，复杂度换不来任何收益）。
- **结构变化**（节点/链接的增删、节点移动、理线改道、小关 Load/Unload）：全部由玩家操作触发、不在 tick 流水线内。Manager 在完成修改后广播**粗粒度通知**（携带数据对象引用），View 响应生成/销毁/重建表现物。
- **全量重建是真相源**：读档、小关 Load 时 View 一律从纯数据全量重建表现；广播只是运行中的增量优化，不是表现的唯一来源。
- 时序推论：单线程下 tick 在一帧内完整执行，View 每帧读到的必然是"完整 tick 之后"的一致快照，不存在半截状态；唯一约定是同帧内**逻辑更新先于表现更新**。

## 3. 时间与模拟模型【已定稿】

### 3.1 固定 tick 推进

- 逻辑层以**固定步长的确定性 tick** 推进（频率具体数值见待定 #5，暂按 10 tick/秒设计）。
- 每个小关维护自己的 `TickCount`（long）。聚焦中的小关由 GameManager 按固定步长驱动。
- **所有速率配置一律以 tick 为单位**（"每 tick 产 X"或"每 N tick 一次"）。
- **逻辑层（ViewModel 全部代码）禁止出现 `Time.deltaTime` / `DateTime.Now` / 无种子随机**。连续感全部由 View 层插值实现（进度条、脉冲移动等）。
- 动机：固定 tick + 固定处理顺序，从根上消除"大量链接同 tick 请求"的时序不确定性，并使存档读档后可精确复现。

### 3.2 tick 流水线：全局三阶段，顺序固定【已定稿】

每个 tick 依次执行：

```
① 投递阶段  所有「在途计时已到期」的持货链接，按目标 Pin 上的
            优先级 + 轮询顺序尝试交付；目标暂存空间不足则部分交付，
            余量留在链接槽位中原地持有。
② 节点阶段  每个节点跑内部逻辑：
            - 资源节点生产（自身暂存满则停产）
            - 加工节点消耗输入暂存、推进配方进度、产出写入输出暂存
③ 取货阶段  所有「槽位为空且到达节拍」的链接，按源 Pin 上的
            优先级 + 轮询顺序向源节点请求物资，装入槽位并启动在途计时。
```

顺序的用意：① 在 ② 前，本 tick 送达的料当 tick 就能进配方；③ 在 ② 后，本 tick 的新产出当 tick 就能被拉走——流水线单 tick 延迟最小。

### 3.3 tick 内竞争仲裁【已定稿】

- 多条链接争抢同一个 Pin（取货或投递）时：**先按优先级分层，同优先级内轮询（round-robin）**。
- 链接带 `Priority` 字段（设置入口见待定 #16）；每个 Pin 维护"上次服务到哪条链接"的轮询指针，随存档序列化。
- 所有遍历按**稳定自增 `LinkId`** 排序（创建时分配、随存档保存），**禁止依赖运行时注册顺序或 Dictionary/HashSet 枚举顺序**——这是存档确定性和后台结算的前提。

### 3.4 未打开的关卡：完全不推进【2026-08-13 改定】

> 本节**取代**原「后台小关稳态结算」方案，待定 #7（稳态算法）随之作废。动机见 §8.5：关卡是一件家具的维修玩法，玩家不在局内时没有理由继续模拟它的产线。

- **同一时刻至多一个关卡推进节点模拟**——玩家正打开的那一个（`LevelManager.ActiveLevel`）。
- 其余关卡数据**常驻内存但完全静止**：`TickCount` 不涨、节点不生产、链接不投递，**也不做任何补账**。玩家再进来看到的就是离开时的样子。
- 唯一继续走的是**家具效果产出**（§8.5）：生效关卡按配置持续产出到 PlayerCargo，走全局 tick，与关卡是否被打开无关。
- 推论：条件节点的滑动窗口以关卡自身 `TickCount` 为时间轴，关卡不推进时窗口内容天然冻结——**生效状态相当于在玩家离开的一刻被锁存**，不需要额外的锁存字段。
- 数据为何常驻而不是卸载：当前没有存档（待定 #9），丢弃 = 玩家布局全没。统一存档接入后可改为「卸载 + 从存档恢复」。

## 4. 网格与空间模型

### 4.1 基础结构

- **Grid（单元格）**：Model 层的最小单位，仅含相对坐标（DeltaPosition）与格子类型。**不含任何运行时状态**（占用与否属于运行时数据，归 ViewModel 的占用索引管，见 §10）。
- **GridGroup**：一组 Grid，承担形状描述与基础查询/碰撞判定。节点占格形状、画布形状都用它表达。
- 节点当前为 n×m 矩形，**后续可能扩展为非规则形状**——一切占格判定必须走 GridGroup 逐格查询，不得假设矩形。
- 画布（原方案中的 CanvasDef）**取消独立类，内联进 LevelDef**（见 §8）。

### 4.2 占格与合法性规则【已定稿】

- 节点占据其 GridGroup 覆盖的格子；**连线同样占据其途径的每一个格子**。
- 合法性检查：连线的每个途径格 必须 ∈ 画布 ∧ ∉ 任何节点占格 ∧ ∉ 其他连线的途径格。
- **连线之间一律不允许共格；连线不可进入任何节点（含中转节点）的占格**，只能接到节点的 Pin 上。
- 推论：两条不同流向的线在空间上"交叉"，唯一途径是接入中转节点的配对 Pin、从对面 Pin 出线（"立交"由配对 Pin 机制实现，不是空间穿越，见 §6.3）。

### 4.3 非法临时态【已定稿】

- 玩家的某次操作（移动节点/链接等）造成冲突时，进入**非法临时态**：
  - 只冻结**本次被移动的对象**（不参与模拟）；移动前合法的其他节点和链接**照常模拟**。
  - 存在任何非法态对象时**禁止存档**；玩家必须解决全部冲突（重新理线或其他操作）后才能存档。
  - **没有任何自动重寻路/自动修复**——修线本身是玩法。
- 正因如此，不需要旧原型那套"棋盘版本号 + 全场链接失效重算"机制。

## 5. 布线系统【2026-08-13 改定：玩家手动描格】

> 原方案 C（创建时一次性 A* 自动布线）**已改**：连线一律由玩家手绘，空间布局是核心玩法，走线自然也该是玩家的作品。

- 连线形态：**格子内的直线 + 直角折线**（4 方向）。
- **创建时**：玩家从 Pin 按下起**描格**——路径跟着鼠标经过的格子逐格延伸，松手时必须落在合法目标 Pin 的接口格上，否则本次绘制作废（不留半截线）。手感细则：
  - 鼠标落回已描过的格 → 截断到那一格（可一次退多格）；
  - 斜向移动 → 自动补一格（优先沿上一段方向先走再转弯，拐角更少）；
  - 撞到非法格（越界/被占用/与自身重叠）→ **停住不延伸、不作废**，玩家绕开继续描。
- **A\* 降级为调试工具**：`LinkManager.FindPath` 保留，唯一调用方是调试面板的「重新布线」按钮。正式玩法不再有任何自动布线。
- **路径合法性一律在 Manager 层复核**（`ValidatePlayerPath`）：不信任 Controller 传入的路径——每格 ∈ 画布 ∧ 未被占用、4 向连续、整条不自交、首尾接在两端 Pin 的接口格上；玩家从输入侧往输出侧画时整条反转后存储（`PathCells` 一律 from→to）。
- **创建后**：玩家可随时抓住线段手动拖排（理线）——**尚未实现**，描格代码就位后它是纯增量。
- **棋盘变化导致走线非法时**：不自动修复，线进入**断线**状态（红色），传输停止，等玩家手工处理。
- `LinkData` 必须存储**玩家著作的折线**（`List<Vector2Int>` 途径格），随存档序列化。

## 6. Pin 与链接

### 6.1 Pin 模型【已定稿】

Pin 是节点上的连接口，类比 UE 蓝图的 Pin。**PinDef 字段**：

| 字段 | 说明 |
|---|---|
| 物资种类 | 该 Pin 传输的 ItemDef（中转节点的配对 Pin 可不预配，运行时同步） |
| 最大速率 | 单次请求的数量上限（"接口访问限流"语义，见 §6.2） |
| 方向 | 输入 / 输出 |
| 配对 Pin | **仅中转节点使用**，指向同节点上的另一个 Pin（见 §6.3） |

- **Pin 自身没有位置概念**；Pin 在节点上的位置（哪个格、朝向哪边）由**所在节点（NodeDef）记录**，由策划手摆。
- 一个 Pin 可接多条链接，仲裁规则见 §3.3。

### 6.2 链接与速率语义【已定稿】

- **链接强类型**：一条链接只运一种物资。连接到输入/输出 Pin 时**自动**根据 Pin 信息确定传输类型。
- **不兼容连接**（两端 Pin 物资类型不同）：链接**清空槽中全部在途物资并停止工作**。这是**有意设计**——此场景下玩家应有丢失产物的心理预期。除此之外全游戏物资守恒（见 §6.4）。
- 速率语义：
  - **输出侧**：链接向源节点发起输出请求（请求量受 Pin 最大速率限制）；节点按优先级+轮询依次尽量满足；剩余资源不足请求量时，仅输出剩余量。
  - **输入侧**：投递受目标节点暂存空间限制——有多少空位收多少，收不下的**留在链接槽位中**（不丢弃、不拒绝后蒸发）。
- 链接自带**节拍**（每 N tick 发起一次取货）与**在途计时**（货物在线上走多久）。数值来源见待定 #4。

### 6.3 中转节点与配对 Pin【已定稿，边角待定 #2】

- 中转节点 = **无配方的加工节点**：不加工、只转运，Pin 位置特殊而密集，用于在狭小范围内为多条链接转向、分流。
- 占格规则与普通节点**完全相同**：链接只能接到其 Pin，不可与其占格重叠。
- **配对 Pin 机制**：例如十字型中转节点，上下为一对、左右为一对。配对 Pin 可不预配物资类型；当一端接到上游的输出 Pin 时，该 Pin 与其配对 Pin 的物资种类**自动同步**，且配对 Pin 自动设为输出方向——直到与最初的上游断开连接为止。
- 边角情况（配对两端同时接上游输出、多个中转节点串成链/环时的类型同步传播）**尚未定案**：待定 #2。实现时先按"后连接的一端报不兼容"占位。

### 6.4 物资守恒与背压【已定稿：链接持货模型】

- **链接持有一个槽位：（物资类型, 数量）**——不是单件，因为 Pin 有速率上限且输出侧允许部分满足。
- 规则：
  1. 投递时目标有多少空位交付多少，**余量留在槽中原地持有**。
  2. **槽位非空 → 不向源头取新货**。这是取货逻辑的前置条件，不是需要维护/解除的状态位。
  3. **投递重试每 tick 照常进行**（参与目标 Pin 的仲裁），目标一腾出空间即交付、槽清空、下个节拍自动恢复取货。
- 背压自然逐跳向上游传导：链接不取货 → 源节点暂存涨满 → **资源节点暂存满时暂停生产**。
- **全游戏无隐性舍弃**。物资消失只有两个**明示**场景，都是有意设计：§6.2 的类型不兼容清空，以及**条件节点收货即蒸发**（§7 条件型：它检查的是供给速率，不是存量，故无暂存、无限吸收，上游因此永不背压）。若未来需要主动销毁，做显式的"垃圾桶/排污"节点。
- View 层收益：TransferPulse（线上脉冲）在阻塞时**停在线上目标门口**，玩家一眼看出堵点——该表现直接由槽位数据驱动，无需额外逻辑。

### 6.5 链接状态机（实现参考）

| 状态 | 条件 | 行为 | 建议表现 |
|---|---|---|---|
| 空闲 | 槽空 | 到达节拍时向源 Pin 请求取货 | 正常色 |
| 在途 | 槽有货，在途计时未到 | 计时推进 | 脉冲沿线移动 |
| 阻塞 | 在途到期但目标无空位 | 持货，每 tick 重试投递；不取新货 | 灰色，脉冲停在目标门口 |
| 断线 | 走线非法（棋盘变化/被移动） | 全部停止，等玩家修线 | 红色 |
| 类型失效 | 两端 Pin 物资类型不兼容 | 清空槽（有意蒸发），停止工作 | 红色/警示图标 |

## 7. 节点类型规格

| 类型 | 输入 | 内部行为 | 输出 | 策划可配 |
|---|---|---|---|---|
| **资源型** | 无 | 按速率生产；**自身暂存满则停产** | 产出物资 | 产出类型、速率、暂存上限、占格形状、Pin 布置 |
| **加工型** | 配方输入 | 消耗输入暂存推进配方（速率可配）；产出入输出暂存 | 配方产出 | 配方、加工速率、各暂存上限、占格形状、Pin 布置（配方选择机制见待定 #3） |
| **仓库型** | 任意（白名单可配） | **漏斗而非容器**：收到即从本关经济中消失，计入全局 PlayerCargo | 无（v1，见待定 #15） | 白名单、占格形状、Pin 布置 |
| **中转型** | 同配对 Pin 同步 | 无配方转运，内部暂存（容量见待定 #6） | 同配对 Pin 同步 | Pin 布置（含配对关系）、占格形状；**位置由策划在关卡中预置** |
| **条件型** | 需求列表中的物资 | **收货即蒸发**、无暂存无限吸收；每条需求统计最近 W tick 的到货量 | 无 | 需求列表 `(物资, 需求量, 窗口 tick)`、占格形状、Pin 布置；**只能预置** |

- 仓库型**无存储上限**顺理成章——它是结算出口，不是容器。**当前关卡不配置仓库节点**（产出出口已上移到家具效果，§8.5），代码保留但事实停用。
- 条件型（2026-08-13 新增）是**家具是否修好的判据**（§8.5）：
  - 多条需求之间「全部满足」才算本节点达标；留空 = 恒达标。
  - 同一物资允许配**多个输入 Pin** 并联供货（单链接速率有上限），到货合并计入同一条需求。
  - 达标每 tick 实时派生，掉下去就掉回不达标（暂不做滞回）。
  - **不可删除、不可由玩家摆放**：按类型强制，调试面板的自由模式也不放行；能否移动由策划在 `PresetNodes` 逐个配。
- `ENodeType` 现为五类：`Resource / Processor / Storage / Transit / Condition`。

### 8.5 关卡即家具【2026-08-13 定稿】

> 落地依据：`Docs/待办工作流/节点系统重构说明.md`。本轮只做到局内 TestScene 可验证，局内外**未打通**，局外侧代码未动。

关卡在游戏中被包装为**房间里的一件家具**，局内玩法 ≈ **维修这件家具**：

- **生效判定**：关卡内没有条件节点 → 恒生效；有则**全部**条件节点达标才生效。非法临时态的条件节点算不达标。
- **判定时机**：每 tick 在节点阶段之后汇总（`LevelManager.UpdateEffective`）。关卡未打开时不重算——生效状态锁存在玩家离开的那一刻（§3.4）。
- **家具效果**（生效后持续产生，两种）：
  1. **生产物资**：按 `LevelDef.Outputs` 逐条计时，产物进 PlayerCargo。计时器走**全局 tick**（不是关卡的 `TickCount`），因此玩家不在局内时照常产出；打烊时随全局停 tick 一起停（§16.4），一天的产能仍然有界。
  2. **装饰分**：数值仍配在家具表 `decorationScore`，关卡只决定"计不计入"。局外侧的过滤（未修好的家具不计分）**本轮未接**，等打通时再做。
- **两条时间轴分工**（容易搞混，实现时务必区分）：

  | 时间轴 | 推进条件 | 谁在用 |
  |---|---|---|
  | `LevelData.TickCount` | 仅关卡被打开时 | 节点模拟、链接节拍/在途、**条件节点的滑动窗口** |
  | 全局 tick | 一直（打烊除外） | 家具效果产出计时 |

## 11. 确定性与存档守则（AI 开发硬规则）

任何人（或 agent）在 ViewModel 层写代码时必须遵守：

1. **禁止** `Time.deltaTime`、`DateTime.Now`、无种子的 `Random`。时间只来自 tick 计数。
2. **禁止**依赖 `Dictionary`/`HashSet` 的枚举顺序；一切遍历按稳定键（LinkId、NodeId、格坐标）排序。
3. 所有速率、时长以 **tick** 为单位。
4. **View 层只读**；数据类只能被 Manager 修改。
5. 存档 = 数据类全量序列化，**必须包含**：轮询指针、节拍/在途计时、持货槽、LinkId 计数器、TickCount。
6. 存在非法临时态对象时**拒绝存档**。
7. 遇到待定项（见下）：留占位符 + 注释标注编号，不自行决策。

## 14. 术语表

| 术语 | 含义 |
|---|---|
| tick | 逻辑层固定步长时间单位，一切速率的分母 |
| 节拍 | 链接发起取货的周期（每 N tick 一次） |
| 在途 | 物资已装入链接槽位、正在线上移动的状态 |
| 持货槽 | 链接上的 (类型, 数量) 缓冲，投递不完的余量留在这里 |
| 背压 | 下游满 → 链接持货不取新货 → 上游暂存涨满 → 停产的逐跳传导 |
| 仲裁 | 多条链接争抢同一 Pin 时的排序规则：优先级分层 + 同级轮询 |
| 稳态结算 | 后台小关不逐 tick 模拟，按瓶颈产率 × Δtick 一次性补账 |
| 非法临时态 | 玩家操作造成冲突后的过渡状态：冻结被移动对象、禁止存档 |
| 配对 Pin | 中转节点上成对的 Pin，类型/方向随上游连接自动同步，实现"立交" |
| 理线 | 玩家手动拖排**已有**连线走线的操作，空间优化玩法的一部分（尚未实现） |
| 描格 | 创建连线的方式：从 Pin 按下，路径跟着鼠标经过的格子逐格延伸（§5） |
| 条件节点 | 检查上游供给速率是否达标的节点，家具「修没修好」的判据（§7） |
| 生效 | 关卡（= 家具）的状态：全部条件节点达标即生效，生效后才产出物资与装饰分（§8.5） |

## 15. 全工程模块化目录规则【2026-08-08 定稿】

> 来源：局外重构访谈（2026-08-08）确定"目录按功能模块划分"后，规则推广到全工程。
> 执行时机：局外重写开工前完成目录重组。**平移是纯机械操作，必须与逻辑重构分开提交。**

### 15.1 原则

- **目录按功能模块划分，模块名必须表达功能含义**。禁止"OutGame/局外"这类只描述位置属性、不含功能语义的伞形命名。
- 模块内部文件沿用 MVVM 分层后缀表达层次：`*Def`（Model，策划配置、运行时只读）、`*Data`（运行时数据）、`*Manager`（逻辑）、`*View`/`*GO`（表现）。**目录回答"属于哪个功能"，后缀回答"属于哪一层"**。
- **命名空间维持单一 `MasterHouse`**（2026-08-08 决策）：快速开发期允许适度耦合换取速度，模块边界靠目录约定维持；后期需要大规模维护时用 Agent 筛查越界依赖，届时再评估子命名空间 / asmdef 硬隔离。

### 15.2 目标结构

```
Assets/Scripts/
  Core/        全局基础设施：GameManager（全局固定 tick 心跳）、GameConfig、统一存档接缝
  NodeSim/     局内节点模拟整体（暂定名）：现有 Data/ViewModel/Manager/View/
               Interaction/Debug/Editor 目录整体平移为其子目录
  Visitor/     访客：配置、到访/服务状态、业务结算、表现（局外）
  Economy/     经济：货币/声望/装饰分（局外）
  HouseClock/  游戏时钟与时段划分（局外）
  Codex/       图鉴资料：设备/档案/世界观/成就/日记（局外）
  Dialogue/    对话接缝（局外，占位模块）
  HouseUI/     局外界面壳：Canvas 生命周期、页面路由、各页面绑定
  Furniture/   家具摆放（局外，现有目录保留）
```

### 15.3 Core 准入标准

**只有局内局外都依赖的东西才进 Core**。单侧使用的工具跟随所属模块：`DebugPanel`/`DebugOptions`（纯局内调试）→ 局内模块，`HouseGmConsole`（局外 GM 面板）→ Economy。当前 Core 只收三样：GameManager、GameConfig、统一存档接缝。将来出现真正通用的框架（如 GM 命令注册机制）再上移——不预设抽象。

### 15.4 局内为何不细拆

局内是强内聚的模拟系统：tick 三阶段流水线（§3.2）横穿节点、Pin、链接、网格、暂存，硬拆成 Node/Link/Grid 多模块只会得到形式上的边界与密集的跨模块引用。局内整体作为一个模块，将来长出真正独立的子系统（教学引导、多关卡管理等）再外拆。

### 16.4 时间模型：并入全局固定 tick【已定稿】

- 局外业务逻辑（时钟推进、时段划分、访客到访/服务窗口判定、周结算）由 **GameManager 的全局固定 tick** 驱动，遵守 §11 全部硬规则。两套时间轴合并为一套。
- 体验节奏沿用"现实 1 秒 = 游戏 1 分钟"，但以 tick 表达（10 tick/秒 → 每 tick = 0.1 游戏分钟），倍率写入 GameConfig 可配字段（待定 #18），禁止散落魔数。
- 时段与到访判定用 tick / 游戏分钟的**整数比较**，禁止 float 小时累加（旧实现的浮点误差不可复现）。
- **表现层豁免**：游走、气泡、错峰入场动画等纯表现留在 View 层，允许无种子随机与 deltaTime；但**表现结果不得回写业务状态**（旧版访客状态机结果回写业务是反例）。
- **打烊闸门【2026-08-10 定，待实现】**：游戏时钟到达当日最晚时刻（打烊）后，**一切 tick 业务统一冻结**——局内生产节点停 tick、局外时钟停止推进、访客的各类倒计时同步停表。动机是堵死"玩家不结束今天、把局内产线挂机无限刷资源"的路子：局外一天的产能上限必须有界。既然生产停了，客人的倒计时也停，语义才统一（否则出现"时间不流动但客人在流失"）。
  - 冻结的只是 tick 业务；局内建造/理线、局外面板操作等玩家交互不在 tick 流水线内（§2.1），照常可用。
  - 解冻由玩家的【结束今天】显式触发：场上尚有未处理访客时该操作不可用，玩家须逐个处理（完成服务或拒绝）；确认后进入当日结算并跳次日开门时刻。
  - 落点：`GameManager.RunTick()` 中的 `LevelManager.TickAll()` 需按营业状态门控（现状无条件执行，见 §12）。

### 16.5 存档：统一存档（待定 #9 已定方向）

- 局内局外同属一次游玩进度，**共用同一份存档**；JSON 文件（persistentDataPath），**禁止 PlayerPrefs**。
- 重写版**先移除局外存档功能**：标题页"继续游戏/读取存档"临时占位（对"功能等价"的明示豁免），只留统一存档接缝；待定 #9 数据结构定案后接入。
- 设置项（音量/窗口模式）不属于游玩进度，独立为全局配置文件（旧版把设置塞进存档槽是反例）。

### 16.6 数据全部 Def 化

- 访客、房间、设备、台词、任务、成就、日记、面板文案等内容数据全部进 Def（SO），遵守 Model 层"运行时只读"。
- **只为已有内容建 Def**，不为策划案 P2 系统（抽卡/社交等）预建结构。
- 手调数值/文案 = 改资产不碰代码；AI 加内容 = 加资产不改代码。禁止新增管道分隔字符串（`"名字|LV.2|效果|1"`）这类无类型数据。

### 16.7 家具子模块：保留 + 断毒点

本轮只做两件事：

2. 家具配置表并入 Def 体系；家具场景层（Controller/Hud/GmConsole）不再依赖局外 UI 工厂。

`FurnitureRoomController`（874 行）内部 MVVM 化、锚点数学双实现合并**推迟到二轮**——策划案对家具玩法后续还有大改（多房间、装饰分玩法），现在拆细可能白做。

### 16.9 对话接缝

- 查证结论（2026-08-08）：项目**无对话系统**——无第三方插件，现状只是带 4 句硬编码台词的访客事务面板。
- 对话系统将**自研**，功能要求后续给出（待定 #17）。重写版只做接缝：台词进 Def；"取对话内容、走对话流程"隔离为独立小接口；自研系统进场时替换接口实现，不动访客业务与 UI。
- **功能要求已给出、设计已定稿（2026-08-11）**，完整规格见 `Docs/待办工作流/对话系统设计说明.md`。与 2026-08-08 的预设相比有两处偏差，以新文档为准：①「不动访客业务与 UI」不再成立——对话事件要驱动访客状态（接待/拒绝就是分支选项上的事件）；②接口不再是单方法取台词，`DefDialogueService` 退役，由 `DialogueManager` 取代（`IDialogueService` 接口本身保留为访客侧的解耦接缝，只改返回值形状）。
- **表现层处置修正（2026-08-12，落地前核查）**：设计说明原文写「旧 `DialogueOverlay` 与 `OutGameDialogueView` Prefab 整体退役、新建纯对话框」，该条**已作废**。另一侧的「对话界面 GVN 化」（commit 1206803）造出的正是设计说明 §10 描述的形态（全屏场景 + 左下立绘 + 底部对话条 + 右侧选项列），点名要删的家具快捷栏已删、访客列表已归 GuestRail、需求展示已归任务卡。故 **Prefab 与 `OutGameDialogueView` 字段袋保留并扩展**（改名会断 Prefab 的 `m_Script` 引用），真正退役的只有 `DialogueOverlay` 内那套临时 debug 选项生成逻辑。经核查该 Prefab 与生成器默认布局逐字节一致、无任何手调，故选项列由固定 7 槽改为「模板 Prefab + 运行时实例化」以符合 §16.2 硬约定（无上限、自动排布）。
- 两条跨模块约束在此备案：**模态对话框期间关闭营业闸门**；**对话事件只做一次性状态转换，后续推进一律由访客状态机负责**（对话可被 ESC 中断，不能承担必发动作）。
- **闸门原因集合的落地形状（2026-08-12）**：`HouseClockManager.SetRunning(bool)` 改为原因集合，但需**区分两个派生量**——`IsRunning`（时钟推进与访客业务 tick，原因 = 不在 Hub 页 + 模态对话框 + 打烊）与 `IsWorldFrozen`（局内产线停 tick，原因 = 模态对话框 + 打烊，**不含**页面闸门）。二者必须分开：局内测试场景没有 HubPage，`IsRunning` 恒 false，若局内产线跟着它门控就永不推进（这正是现状只用 `IsClosedForToday` 门控 `LevelManager.TickAll()` 的原因）。打烊仍是时间的纯函数派生、不入集合，真正的持有者只有「页面」与「模态对话框」两个。
