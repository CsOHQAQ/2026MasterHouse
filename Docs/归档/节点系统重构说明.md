## 0. 一句话

关卡的定位从"独立小关"变为**一件家具的维修玩法**：条件节点判定家具是否修好，修好的家具在局外持续产出物资与装饰分；连线从"创建时自动 A\*"改为**玩家手动描格绘制**。

## 1. 改动总览

| # | 改动 | 影响面 |
|---|---|---|
| 1 | 新增**条件节点**（第五种节点类型） | Data / ViewModel / Manager / View / Editor / DebugPanel |
| 2 | 关卡绑定家具 + **生效判定** | LevelDef / LevelData / LevelManager |
| 3 | 生效家具的**效果产出**（物资进 PlayerCargo；装饰分不在此配） | LevelDef / LevelManager |
| 4 | Load/Tick **拆两层**：数据常驻、只推进打开中的关卡 | LevelManager / ViewManager / InteractionController / DebugPanel |
| 5 | 连线改为**手动描格绘制** | InteractionController / LinkManager |

仓库节点（`StorageNodeDef`）代码**保持原样**，只是关卡不再配置它 → 事实上停用。`PlayerCargo` 的入口随之从"仓库节点投递"变为"家具效果产出"。

## 2. 条件节点

### 2.1 Def

```csharp
public enum ENodeType { None, Resource, Processor, Storage, Transit, Condition }   // 新增 Condition

[Serializable] public class ConditionEntry
{
    public ItemDef Item;         // 需求物资（水、电这类）
    public int RequiredAmount;   // 窗口内需累计收到的量
    public int WindowTicks;      // 滑动窗口长度
}

public class ConditionNodeDef : NodeDef      // Assets/Scripts/NodeSim/Data/ConditionNodeDef.cs
{
    public override ENodeType NodeType => ENodeType.Condition;
    public List<ConditionEntry> Conditions = new List<ConditionEntry>();
}
```

- 多条条件之间是**全部满足**。
- Pin 照常在节点编辑器手摆并配物资类型，**同一物资允许多个输入 Pin**（单链接速率有上限，靠并联堆速率），到货合并计入同一条条件。
- 编辑器校验：条件表里出现的物资必须有对应的输入 Pin，缺则窗口内报警告（不阻塞保存）。

### 2.2 运行时

`NodeData` 新增 `ConditionState`（仅条件节点非 null，与现有 `InputStorage`/`OutputStorage` 同型，构造函数 switch 里初始化）。

- **不设暂存**：收到即蒸发，无限吸收。这是 §6.4「全游戏物资守恒」的**第二个明示例外**（第一个是 §6.2 类型不兼容清空），需写进架构文档。
- 每条条件维护一个**到货记录队列** `(tick, 数量)`：收货追加，每 tick 弹出 `tick <= 当前TickCount - WindowTicks` 的记录。到货是稀疏的（链接按节拍成批送达），队列远短于窗口长度——**不要用每 tick 一格的环形数组**。
- `IsSatisfied`（每条）= 队列内累计 ≥ `RequiredAmount`；节点整体达标 = 全部条件满足。每 tick 重算，可掉回不达标；暂不做滞回（实测觉得闪再加"连续 N tick 不达标才判失效"的宽限）。

### 2.3 接入 tick 流水线

| 阶段 | 改动 |
|---|---|
| ① 投递 | `LinkManager.GetDeliverSpace` → Condition 返回 `int.MaxValue`（无限吸收，**上游因此永不背压**，这是有意的）；`Deposit` → 记入条件窗口。`Deposit`/`DeliverToPin` 需要多传一个 `long tick` 参数（当前签名拿不到 `TickCount`） |
| ② 节点 | 新增 `case ENodeType.Condition` → 弹过期记录、重算达标 |
| ③ 取货 | 无（条件节点没有输出 Pin） |

顺序上①在②前，本 tick 送达的货当 tick 计入窗口，与既有流水线语义一致。

### 2.4 约束与配置

- **不可删除**：`RemoveNode` 前的资格校验按类型强制拦下（不只是 `CanDelete` 字段，自由模式也不放行——它是关卡的判据，删掉等于关卡失去意义）。
- **不可由玩家摆放**：不进 `BuildableNodes`；`CanBuild` 对条件节点一律返回 false，调试面板的自由模式生成列表也排除它。
- **能否移动**由策划在 `PresetNodes` 里逐个配 `CanMove`。

### 2.5 表现

- `NodeGO`：新增配色（暂定青色）；头顶显示每条条件的窗口进度，如 `水 3/5`，达标标记颜色区分。
- `DebugPanel`：选中条件节点时列出各条条件的窗口累计 / 需求 / 达标与否。

## 3. 关卡绑定家具、生效判定与效果产出

### 3.1 LevelDef 新增字段

```csharp
public string FurnitureId;                        // 关联家具表的行 id
public List<FurnitureOutputEntry> Outputs;        // (ItemDef Item, int Amount, int TicksPerOutput)
```

- 家具**不是独立资产**，是 `FurnitureTable`（Excel → CSV → 整表重建的 SO）里的一行，所以只能用 `string id` 关联。关卡编辑器窗口把这个字段做成**从家具表读 id 的下拉选择**，策划不手打字符串。
- **装饰分不在这里配**（访谈定案 a）：数值继续留在家具表的 `decorationScore` 一列，关卡只决定生不生效。局外侧的过滤（未修好的家具不计分）等打通时再接，本轮不做。
- 产出表多条并行，每条各自计时。

### 3.2 生效判定

`LevelData.IsEffective`：

- 关卡内**没有**条件节点 → 恒为 true。
- 有条件节点 → **全部**达标才为 true。
- 每 tick 在节点阶段之后重算；关卡数据创建时先算一次（有条件节点则初值 false）。
- **锁存是自然结果**：玩家退出局内后关卡不再 tick，`IsEffective` 保持最后一次的值不变。不需要额外的锁存字段。

### 3.3 效果产出

- 产出计时器 `LevelData.OutputCounters`（每条产出一个），**每 tick 都推进**，与关卡是否被打开无关。
- 到点则 `PlayerCargo.Add(Item, Amount)`。
- 打烊时全局停 tick（§16.4），家具产出跟着停——正好兑现"一天产能必须有界"。

**注意 `TickCount` 与产出计时的分工**：`LevelData.TickCount` 只在关卡被打开时推进（它是节点模拟的时间轴，条件节点的滑动窗口也用它），所以退出局内后窗口内容天然冻结、再进来仍是达标状态；产出计时器走全局 tick，独立推进。两条时间轴分开，不要混用。

## 4. Load/Tick 拆两层

现状 `LevelManager.loadedLevels` 一个列表同时表达"数据存在"和"要推进"，本轮拆开：

| 概念 | 落地 |
|---|---|
| 数据常驻 | `List<LevelData> levels`（按创建顺序，稳定；**不用 Dictionary 枚举** §11.2） |
| 正在推进 | `LevelData ActiveLevel`，同一时刻至多一个 |

- `EnsureLevel(LevelDef)` → 创建或取回常驻数据；`OpenLevel(LevelDef)` / `CloseLevel()` → 进出局内。
- 关卡数据**必须常驻内存**：现在没有存档（待定 #9），关掉就丢等于玩家布局全没。等统一存档做完再改成"卸载 + 从存档恢复"。
- `TickAll()` 改为两段，顺序固定：**先**推进 `ActiveLevel` 的节点三阶段（更新 `IsEffective`），**再**对**所有**常驻关卡推进效果产出。这样本 tick 修好的家具当 tick 就开始产出。
- 事件 `OnLevelLoaded`/`OnLevelUnloaded` 语义改为 `OnLevelOpened`/`OnLevelClosed`（View 只表现 `ActiveLevel`）；`ViewManager`、`InteractionController.CurrentLevel`、`DebugPanel` 跟着改。
- 调试面板的**热重载**语义不变（丢弃该关 `LevelData` 重建），只是改走新的丢弃接口。

**这条同时废掉 §3.4「后台小关稳态结算」与待定 #7**——新规则是"玩家不在局内就完全不更新节点"，与稳态补账互斥。

## 5. 手动描格连线

### 5.1 交互（`InteractionController`）

1. 在 Pin 上按下 → 进入描格，路径起点 = 该 Pin 的**外侧接线格**（`NodeData.GetPinPortCell`）。
2. 拖动过程中，鼠标所在格与路径末端不同时：
   - 该格**已在路径中** → 截断到那一格（允许一次退多格，鼠标快也不卡）；
   - 否则按曼哈顿路径补全中间格，**优先沿上一段方向先走一格再转弯**（没有上一段时先走横向），逐格校验；
   - 遇到非法格（出画布 / 被占用 / 与自身路径重叠）**停住不延伸、不作废**，玩家绕开继续画。
3. 松手：路径末端 == 目标 Pin 的外侧接线格，且鼠标命中该 Pin → 创建；否则**整次作废**（静默）。
4. 预览：现有的两点直线 `LineRenderer` 改为沿路径的折线渲染。

### 5.2 Manager（`LinkManager`）

- `TryCreateLink` 增加可选参数 `IReadOnlyList<Vector2Int> path`：为 null 时走 A\*（调试面板"重新布线"用），非 null 时**校验玩家路径**——每格 ∈ 画布 ∧ 未被占用、4 向连续、不自交、首尾格分别是两端 Pin 的外侧接线格。
- **路径校验必须在 Manager 层**，不得信任 Controller 传入（"占格合法性在 Manager 层，任何路径不可绕过"）。
- 方向解析可能把 `pinA/pinB` 反转成 `from/to`，此时**路径要一并反转**再存入 `PathCells`。
- 其余校验（方向、类型推导、仓库白名单、中转同步）原样复用。
- `FindPath`（A\*）**保留**，只服务调试面板。

## 8.5 落地记录（2026-08-13，代码已完成）

本节记录**文档没覆盖、落地时补的决策**，以及实现上的取舍。设计本体未变。

| 项 | 落地结论 |
|---|---|
| 条件节点的"不可删除" | 在 `LevelManager.RemoveNode`（Manager 层，返回 false）、`InteractionController`（提示文案）、`PlacementController.BeginPlacement`（不可摆放）、`CanBuild`、调试面板生成列表 **五处都拦**。自由模式一律不放行 |
| 同 tick 多次到货 | `ConditionState.Record` 把同一 tick 的多笔并入队列最后一条，队列更短；窗口口径 `Tick ∈ (当前 - W, 当前]` |
| 关卡生效的初值 | `EnsureLevel` 创建后立即算一次：有条件节点则初值 `false`（家具刚摆下＝没修好） |
| 非法临时态的条件节点 | 算作不达标（它被冻结、窗口不推进），关卡随之失效 |
| 切关 vs 关闭 vs 热重载 | 调试面板三条路径分开：点其他关 = `CloseLevel` + `OpenLevel`（旧关数据留着）；点当前关 = `DiscardLevel` + `OpenLevel`；「关闭关卡」按钮 = 纯 `CloseLevel`（验证退出局内后产出继续） |
| 描格的终点判定 | 优先取鼠标命中的 Pin，没命中则**按路径末端反查 Pin**——玩家把线画到接口格上就算连到，不必再精确悬停在 Pin 标记上 |
| 描格的防御 | 单帧跨格补全加 256 步上限（鼠标跨屏跳跃时防死循环）；路径合法性在 `LinkManager.ValidatePlayerPath` 完整复核，不信任 Controller |
| 路径方向 | 玩家可能从输入侧往输出侧画，`ValidatePlayerPath` 检出后整条反转，`PathCells` 存储一律 from→to |
| 关卡编辑器的家具下拉 | 每次绘制重建选项（家具行数少），新导表立刻生效；家具表缺失时退回手填文本框 + 警告，不阻塞关卡编辑 |
| 关卡校验新增 | 产出条目字段校验；「没有条件节点却配了产出」提示恒定生效；「条件节点被塞进可建列表」报错 |
| `LevelDef` 新字段的编辑器 | `Outputs` 由 `DrawAutoFields` 的 SerializedObject 自动绘制（该窗口本就是加字段零维护），只有 `FurnitureId` 做了定制下拉 |
| 编译验证 | `dotnet msbuild` 离线编译 `Assembly-CSharp` 与 `Assembly-CSharp-Editor` 均通过。两个新增 .cs 已手工加进 `Assembly-CSharp.csproj` 的 Compile 列表（Unity 下次生成 csproj 会自动包含，无副作用） |
| **未做** | 种子资产（条件节点 Def、需求物资、关卡上的预置与产出配置）——新脚本还没有 .meta GUID，无法离线生成 `.asset`，需在 Unity 内用编辑器窗口创建，步骤见测试场景使用说明 §6.1 |

## 9. 验收清单（TestScene 内实跑）

- [ ] 条件节点无法被玩家删除、不出现在生成列表（含自由模式）
- [ ] 给条件节点供货：窗口累计达到需求 → 节点显示达标；断掉上游一段时间 → 掉回不达标
- [ ] 同一物资接两个输入 Pin，到货合并计入同一条条件
- [ ] 关卡内所有条件节点达标 → 面板显示关卡生效；任一掉线 → 失效
- [ ] 无条件节点的关卡恒显示生效
- [ ] 生效期间 `PlayerCargo` 按 `Outputs` 配置持续增长；失效则停
- [ ] 退出关卡（Close）后：节点不再推进、`TickCount` 不涨，但产出照常增长
- [ ] 重新打开关卡：布局与达标状态原样保留
- [ ] 描格连线：撞墙停住可绕行、退回可截断、非 Pin 处松手作废、连到合法 Pin 成线
- [ ] 玩家画出的折线被完整保存并用于脉冲插值（不是被 A\* 覆盖）
- [ ] 调试面板"重新布线"仍走 A\*
