# 访客系统实现交付说明

> 创建：2026-08-10。本文件是**给接手开发者的实现说明**，不是决策讨论稿——文中所有条目均已由用户拍板，可直接开工。
> 权威依据：`Docs/架构设计.md`（尤其 §11 确定性与存档守则、§15 目录规则、§16 局外系统架构）。本文与架构设计冲突时以架构设计为准；本文新增的决策已同步回写 §16.4。
> 现状地图：`Docs/局外系统说明.md`。
> **对话系统不在本文范围**：访客侧只需在状态转换点调用对话触发接口（§8），对话系统本体另有设计文档，由另一路并行推进。
> 遇到本文标注【待确认】的条目，按给出的默认值实现并留注释，不要自行改设计。

---

## 1. 一句话目标

把访客从「策划手配的 4 个固定角色 + 一个 Serve 按钮」重做为**种族模板 → 日程表驱动生成的运行时实例**，走完整的五段生命周期，服务结果由**物品 tag 匹配**判定满意度。

## 2. 现状差距（开工前必读）

| 目标 | 现状 | 处置 |
|---|---|---|
| 种族模板 + 运行时实例 | `VisitorDef` 手配 4 个完整访客（`VisitorTable.asset`） | `VisitorDef`/`VisitorTable` 退役，重建为 `VisitorRaceDef` + 日程表 |
| 五态生命周期 | `VisitorState` 只有 `Arrived`/`Served`/`Refused` 三个 bool | 重写为状态枚举 + 计时 |
| 两段超时 | 无任何计时器；靠 `serviceStart/serviceEnd` 服务窗口 | 服务窗口退役，改超时 |
| 日程表 | 无；`visitHour` 写在访客身上 | 新建 `VisitorScheduleTable` |
| 需求 = tag | `need`/`solution` 两个自由文本 string | 新建 `TagDef` 体系 |
| 提交物品 | `Serve(index)` 直接结算，无物品 | 接 `PlayerCargoData` |
| 满意度 | 无 | 新建四档枚举 |
| 打烊闸门 | `LevelManager.TickAll()` 无条件执行 | 见 §7 |
| 一天的结束 | `EndWeek()` 手动按钮 + 周制 | 周制退役，改日结 |

## 3. 目标结构总览

```
Model（Def，运行时只读）
  TagDef                 需求/物品标签，单亲父链构成森林
  ItemDef      （扩展）   += List<TagDef> tags     ← 局内局外共用
  VisitorRaceDef         种族模板：性格数值 + 需求权重 + 立绘差分 + 对话池引用
  VisitorScheduleTable   日程表：第几天 / 出现时刻 / 种族
  VisitorTuningConfig    全局表现与营业参数

ViewModel
  VisitorInstance        运行时访客实例（状态、计时、需求、评分结果）
  VisitorData            当前在场实例集合 + 日程游标
  VisitorManager         生成、状态推进、超时、接待/拒绝/提交结算（挂全局 tick）

View
  OutGameVisitorStage / Actor / Bubble / SheetAnimator（平移改接实例列表，§9）
```

目录：全部落在 `Assets/Scripts/Visitor/`，命名空间 `MasterHouse`（§15.1，不设子命名空间）。`TagDef` 因局内局外共用，放 `Assets/Scripts/Core/`（符合 §15.3 准入标准：两侧都依赖）。

## 4. 数据结构规格

### 4.1 TagDef（`Core/TagDef.cs`，ScriptableObject）

```
id            稳定键（存档/日志用）
displayName   显示名，如「甜」
描述词         造句用短语，如「甜的」
parent        TagDef 引用；null 表示自己是某条轴的根
语法角色       仅根节点填写，后代继承。枚举：名词 / 形容词
sortOrder     同层排序，保证造句与展示顺序稳定（§11.2）
```

- **森林结构**：每棵树的根即一条「轴」（品类 / 口味 / 质地 …），不再单独建轴枚举。
- **匹配规则**：需求 tag 命中 ⇔ 物品的某个 tag 等于它、或以它为祖先。物品只需标最具体的叶子。
- **编辑器校验（必做）**：父链成环报错；跨轴同名/同义 tag 给警告。跨轴语义必须正交——`口味/甜` 与 `品类/甜点` 这类重叠是配置事故的高发点。
- 遍历一律按 (轴 sortOrder, 节点 sortOrder) 排序，**禁止依赖资产枚举顺序**（§11.2）。

### 4.2 ItemDef 扩展（`NodeSim/Data/ItemDef.cs`）

只加一个字段：`public List<TagDef> tags`。不要为局外另建一套物品 Def——**招待访客就是 `PlayerCargoData` 的消费出口**（这同时回答了待定 #15 的「v1 只进不出？」：出口就是这里）。

### 4.3 VisitorRaceDef（ScriptableObject，一个种族一个资产）

```
身份       raceId / 显示名
性格数值   等搭话超时(tick) / 等交货超时(tick) / 闲逛时长上限(tick) / 跨天留宿概率
需求生成   needTagWeights: [(TagDef, 权重, 是否必要)]  +  需求数量范围 [min, max]
表现       立绘差分表：表情枚举 → 贴图路径；序列帧路径
对话       对话池引用（类型由对话系统交付时给出，先留字段占位）
```

> **现状修订**：上表是 2026-08-08 的原始设计，之后逐条改过，`VisitorRaceDef` 现在长这样：
>
> ```
> 身份       raceId / 显示名
> 性格数值   等搭话超时(tick) / 等交货超时(tick) / 闲逛时长上限(tick)
> 表现       defaultPortraitId（立绘表主键）/ sheetPath（序列帧前缀）
> ```
>
> - **需求生成**整段随 tag 需求体系退役（2026-08-13，需求重做说明 §9.1）：谁带什么需求来由日程条目配死。
> - **对话池引用**随对话资源重构删除（2026-08-14）：对话内容按 `raceId` 查 `DialogueTable`。
> - **跨天留宿概率**删除（2026-08-14）：闲逛访客的跨天 roll 早已移除，字段自那时起就没有消费方。
> - **立绘差分表**删除（2026-08-14 立绘 ID 化）：表情枚举退役，立绘搬到独立的
>   `Excel/立绘表.xlsx` → `PortraitTable`，种族只留一个「默认长什么样」的 ID。

「这个种族是什么性格」的数值全在这里（急性子超时短、熟客爱赖着不走）。**没有覆写机制**，每个数值只有一个家。

### 4.4 VisitorScheduleTable（ScriptableObject，单资产多行）

```
entries: [ { day: int, 出现时刻: 分钟(0~1439), race: VisitorRaceDef, 具名覆写: NamedVisitorDef(可空) } ]
```

- **零随机、零上限**：谁在第几天几点出现，完全由策划配。不做生成器，不做同时在场上限。
- 条目按 (day, 出现时刻, 下标) 稳定排序后消费。
- 【待确认】日程跑完最后一天之后的行为。默认实现：**停止投放新访客**（日志给一条 Warning），等策划补内容。
- `NamedVisitorDef`（具名剧情客人覆写：固定名字/立绘/需求/专属对话）先建结构留空实现——现阶段无内容，按 §16.6「只为已有内容建结构」，可以只留字段不建资产。

### 4.5 VisitorTuningConfig（全局 ScriptableObject）

```
营业时段    开门时刻 / 打烊时刻（分钟）
闲逛节奏    冒泡间隔(tick) ± 抖动 / 气泡停留时长(tick)
```

`HouseClockManager.DayStartMinute` 这个 `const 8*60` 要迁进本配置（开门时刻），代码里不再留营业时间魔数。

### 4.6 VisitorInstance（运行时数据类）

```
instanceId     稳定自增，序列化（遍历排序键，§11.2/11.3）
race           ref VisitorRaceDef
scheduleDay / scheduleIndex   来源日程条目（重算派生种子用，§6）
state          EVisitorState
stateEnterTick 进入当前状态的全局 tick（算超时用）
needs          List<需求项>，需求项 = (TagDef tag, bool required)
satisfaction   EServeSatisfaction（Done 之后有效）
submittedItem  ref ItemDef（结算展示与日志用）
```

只能由 `VisitorManager` 修改（§11.4）。

enum EServeSatisfaction { 不对味, 一般, 满意, 完美 }

## 5. 生命周期状态机

```
日程到点 → 【前台等待接待】
              ├ 玩家交互 ─→ 播【初次见面】对话（状态不变，仍在前台）
              │                └ 对话末尾分支的选项事件驱动 ↓ 两条
              ├ 接待 ─→ 【服务中】进入房间，播【开始等待服务】+ 程序化需求句
              │            ├ 提交物品 → 评分（§6.2）
              │            │     ├ 不对味 → 播【完成服务·不对味】→ 直接离开（不进闲逛）
              │            │     └ 其余三档 → 播【完成服务·对应档】→ 【闲逛】
              │            └ 等交货超时 → 播【被拒绝】→ 离开
              ├ 拒绝 ─→ 播【被拒绝】→ 离开
              └ 等搭话超时 ─→ 播【被拒绝】→ 离开

【闲逛】 ── 每隔 (冒泡间隔 ± 抖动) tick 自动抽一句闲逛台词冒泡
        ├ 累计闲逛时长 ≥ 种族上限 → 离开
        └ 打烊时仍在闲逛 → 按种族「跨天留宿概率」roll，中了则保留到次日
```

> **修订（2026-08-14）**：最后那条跨天留宿 roll **已删除**。服务中/待分房本来就无条件跨天，
> 单给闲逛的掷一次骰子不一致；现在统一按停留时长走，到点自己离开。
> `VisitorRaceDef.stayOvernightPercent` 与种族表的「跨天留宿概率%」列已随之清理。
> 日结面板上的「跨天留宿 N 位」是**实际留宿人数统计**，与这个 roll 无关，仍然照常显示。

要点：

- **需求是接待之后才提的**，不是初次见面时。初次见面对话只负责打招呼 + 给出接待/拒绝的选择。
- **服务一次性、不可补交**：`服务中` 是不可重入的单向状态，提交一次即定生死。交错了照样扣物品、访客直接离开。
- **拒绝在「前台等待接待」和「服务中」两个状态都可用**（打烊后玩家必须能手动清场）。
- 两段超时**都走【被拒绝】对话分类**并按拒绝口径结算声望。
- 所有计时以 tick 为单位、整数比较（§11.3）；**禁止** `Time.deltaTime` / `DateTime.Now`（§11.1）。

## 6. 需求生成与确定性随机

### 6.1 派生种子（无状态）

```
rollSeed = Hash(runSeed, scheduleDay, scheduleIndex)
```

- 每条日程独立推导自己的随机流，**不依赖调用顺序、不需要序列化 RNG 内部状态**；同一个客人无论何时重算都得到同一份需求，读档刷需求的路子被堵死。
- `runSeed` 是一个 `long`。**存档系统未落地期间**（待定 #9），由启动/GM 层注入一个固定默认常量并允许 GM 面板改写——注意这样过渡期也不存在无种子随机，不违反 §11.1。存档接入后 `runSeed` 改为存档字段。
- 自己实现一个确定性 RNG（如 xorshift / PCG），**不要用 `UnityEngine.Random`**（全局状态、跨平台不保证一致）。

### 6.2 需求 roll 与评分

- 从种族的 `needTagWeights` 里按权重抽 `需求数量范围` 内的若干项，标了「是否必要」的按其配置落到需求项上。
- 【待确认】**抽到树的哪一层**（抽 `食物` 还是抽 `蛋糕`）是难度旋钮的本体，策划案未明确。默认实现：**在权重表里随机抽，不做层级控制**；后续策划案给出规则再调整，实现时把这段抽取逻辑收在一个方法里方便替换。
- 评分：
  1. 任一 `required` 需求项未命中 → **不对味**。
  2. 否则按加分项命中比例分档：`< 阈值A` → 一般；`≥ 阈值A 且 < 100%` → 满意；加分项全命中 → **完美**。
  3. 需求项里没有加分项（只有 required）时直接判**完美**。
- 阈值 A 与四档各自的货币/声望奖励配在 `EconomyConfig`。现有 `serviceCurrencyReward` / `serviceReputationReward` 是单值，需扩成按档配置；`refuseReputationPenalty` 沿用于拒绝与两段超时。`failReputationPenalty` 与 `FailGuestServices(int)` 随周制一并退役。

## 7. 打烊闸门与日结（详见架构设计 §16.4）

- 到达打烊时刻后，**一切 tick 业务统一冻结**：局内生产节点停 tick、局外时钟停止推进、访客各类倒计时停表。动机是堵死「不结束今天、挂机无限刷资源」。
- 冻结的只是 tick 业务；玩家交互（局内建造/理线、局外面板）照常可用。
- 解冻由玩家点【结束今天】显式触发：**场上仍有未处理访客时该按钮不可用**，玩家须逐个处理（完成服务或拒绝）；闲逛中的访客不阻塞。
- 确认后进入当日结算面板 → `Day+1`，时间跳到次日开门时刻。
- 日结**只展示不惩罚**——惩罚已在超时/拒绝当时结清，不重复扣。
- 落点：`GameManager.RunTick()` 里的 `LevelManager.TickAll()` 需按营业状态门控（现状无条件执行）。

## 8. 与对话系统的接口（本文只定契约）

访客侧需要在状态转换点请求播放对话，并接受对话事件对业务的驱动。**两侧各出一半，签名以对话系统交付文档为准**，本文只固定契约形状：

**访客 → 对话**：五个触发点

```
初次见面      进入「前台等待接待」后，玩家交互时
开始等待服务   接待成功、进入「服务中」时（含程序化需求句）
被拒绝        玩家拒绝 / 等搭话超时 / 等交货超时
完成服务      提交结算后，附带 EServeSatisfaction 作为筛选键
满意后闲逛     闲逛期间由冒泡调度器定期请求
```

**对话 → 访客**：对话事件需要能驱动这三个业务动作，`VisitorManager` 必须暴露为公开方法且自带合法性校验（状态不对时返回 false 而不是抛异常）：

```
bool Accept(int instanceId)                        接待
bool Reject(int instanceId)                        拒绝
bool Submit(int instanceId, ItemDef item)          提交物品并结算
```

对话系统未落地期间，允许在 UI 上挂**临时 debug 按钮**直接调这三个方法，用于验证访客状态机——这是明示许可的临时代码，接入对话系统时删除。
