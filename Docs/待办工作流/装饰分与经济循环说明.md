## 1. 一句话目标

把**装饰分**从只显示不生效的死值变成「按房间生效、提高该房客人离场小费」的真实循环；家具改为**可重复购买**让货币有长期去处；**声望改为只增不减**堵掉死锁；并给 demo 一个明确结局。

## 2. 现状诊断与目标模型

三值循环里只有装饰分是断头路，代码注释三处明写（`EconomyManager.cs:67`、`EconomyConfig.cs:19`、`:52`）：「装饰分**无去处**」。而且它三个来源里**两个是常量**——房间数固定 4、设备数取自 `CodexTable` 固定，唯一变量是已摆家具的 `decorationScore` 之和。

| 值 | 现状来源 | 现状去处/作用 | **改后** |
|---|---|---|---|
| 货币 | 离场小费 + 服务奖励 + 对话事件 | 买家具（每种限一件） | 小费**受房间装饰分加成**；家具**可重复买**，货币有长期去处 |
| 声望 | 服务奖励 + 对话事件 | **仅玩家主动拒绝**扣除（两段超时早已不扣，见 §5.1）；作用 = 家具解禁门槛 | **只增不减**，惩罚全部移除；作用不变 |
| 装饰分 | 房间数×50 + 设备数×30 + 家具得分 + GM | **无** | **按房间生效**：提高该房客人的离场小费 |

一个现成的便利：`FurnitureRoomController.SyncDecorationFromSession()` 已经在**逐房间**计算，只是最后求和成全局值。按房间的数据不用新建。

## 3. 装饰分按房间生效

### 3.1 取分口径

**按访客离场时所在的房间取分**，规则统一，不为任何情况特判：

| 情况 | 取哪间房 |
|---|---|
| 入住客房、正常完成服务后闲逛离开 | 所住客房 |
| 闲逛期间被玩家拖去别的房间 | 拖到的那间（当前 `RoomIndex`） |
| 前台等搭话超时 / 在前台被拒绝 | **大堂（房间 0）**——他们的 `RoomIndex` 本来就是 0 |
| 服务中被拒绝 / 等交货超时 | 所住客房 |

好处：大堂装修也有回报（覆盖流失的客人），且「没入住的客人算哪间房」自动有答案。

### 3.2 公式

```
离场小费 = guestLeaveTip + 该房间装饰分 × tipPerDecorScore
```

- **线性、无封顶**：房间格子数本身就是硬上限，不需要人为封顶。
- 全整数运算（§11.3）。`tipPerDecorScore` 新增到 `EconomyConfig`，【待确认】默认 `1`。

### 3.3 代码改动

| 位置 | 改动 |
|---|---|
| `Furniture/FurniturePlacementQuery`（需求包已建） | 新增 `int DecorationScoreOf(int roomIndex)`。**沿用同一套 null 回落**（`CaptureSessionPlacements(roomId) ?? room.initialPlacements`），漏了会让没编辑过的房间恒为 0。**桌面家具（`hostFurnitureId` 非空的）同样计入**——客人不关心杯子放在地上还是茶几上 |
| `EconomyConfig` | 新增 `tipPerDecorScore` |
| `EconomyManager.GuestLeaveTip()` | 改签名为 `GuestLeaveTip(int roomDecorScore)`。**不要让 EconomyManager 去查家具**——保持它对家具模块的单向依赖 |
| `VisitorManager.Depart(instance)` | 调用处先取 `FurniturePlacementQuery.DecorationScoreOf(instance.RoomIndex)` 再传入 |
| `EconomyManager.DecorationScore` | **保留不动**，仍是全局展示值，HUD 照旧 |

### 3.4 UI：让因果链可见

装修 → 小费这条循环，玩家**感知不到就等于不存在**。三处都要做：

1. **房间装饰分**：家具模式 HUD（摆家具时实时变化，反馈最直接）＋ Hub 当前房间信息处。
2. **日结面板拆分小费与服务奖励**：现在把两者都算进 `summary.CurrencyEarned` 一个数（`VisitorManager.cs:758` 的小费与 `:552` 的服务奖励），玩家**看不出"装修给我多赚了多少"**。改动：`VisitorDaySummary` 拆出 `TipEarned`，`Depart` 里累加到它而不是 `CurrencyEarned`，日结面板分两行显示（如「服务奖励 +1200 / 客人小费 +860」）。
   ⚠ **落点已变**（2026-08-15 核实）：日结文案现在由 **`HouseUI/DayTransitionFx.cs:150-160`** 拼装（`a9d6c32` 把结算讯息并进黑夜→白天过场并移到左上角），原文提到的 `DaySettleOverlay.BuildBody` **已不存在**。
3. 【待确认】是否顺带显示「本房客人小费预计 +N」：**默认显示**——因果链越短玩家越容易理解。

> **已知不对称（落地时在注释里写明）**：`Data.GmDecorationBonus` 只进全局展示值 `DecorationScore`，**不进任何房间**，因此 GM 调装饰分测不出小费变化。要测小费加成必须真的往房间里摆家具。修正它需要给 GM 加成指定归属房间，收益不值当，故维持现状。

## 4. 家具可重复购买

### 4.1 为什么改

三间客房可能同时有客人要同款家具；且家具全买完之后货币就没有去处了。

### 4.2 ⚠ 先修一个现存漏洞

`FurnitureRoomController.IsPlaced(furnitureId)`（`:421`）只遍历 `items`——**当前打开房间**的运行时实例，不跨房间。

所以四宫格改造之后，「每种家具只能拥有一件」这条规则**早已形同虚设**：同一张沙发可以在四个房间各摆一份。改成可重复购买后若不修，玩家买 1 件仍能摆 4 个。

> **本条待核实**：需确认这是否为四宫格改造时的有意设计。若确认为有意（允许一件家具同时出现在多个房间），本节与 §4.5 的余量口径需改写为按房间独立计算。

**正确口径：可摆余量 = 拥有数 − 全部房间已摆放数。** 已摆放数必须遍历 `sessions` 的**所有房间**（当前房间取实时 `items`，其余取会话布局，未编辑过的回落 `initialPlacements`）。与 §3.3 是同一个坑。

### 4.3 数据结构

| 位置 | 改动 |
|---|---|
| `EconomyData.OwnedFurniture` | `HashSet<string>` → `Dictionary<string, int>`（id → 拥有数） |
| `IsFurnitureOwned(id)` | 保留，语义 = 数量 > 0 |
| 新增 `OwnedCountOf(id)` | 拥有数 |
| `TryPurchaseFurniture` | 删掉 `AlreadyOwned` 分支，改为数量 +1；解禁与货币两道门不变 |
| `FurniturePurchaseResult.AlreadyOwned` | 废弃（保留枚举值占位或删除，删时检查全部 switch） |
| `AddFreeFurniture()` | price ≤ 0 的家具**置为 1 件而不是累加**——它在 `ApplyDefaults` 与 `Restore` 里都被调用，用 `+=` 会导致读档后数量翻倍 |
| `EconomySaveData.ownedFurniture` | 改为带数量的结构。**序列化前按 id 排序**（§11.2）。注意存档本身不做（§6），但快照接缝要跟着改 |

### 4.4 商城 UI 语义重定义

`StoreOverlay` 对「已拥有」这个二元状态依赖很深，逐处重定义：

> 行号按 2026-08-15 复核（`67b36e5` 商店改造后整体下移了十几行）。

| 位置 | 现状 | 改为 |
|---|---|---|
| `:422-427` 色块变暗 | 该配色已拥有 | 语义改为「已有此配色（≥1 件）」，**表现不变** |
| `:277` `ChoiceOf` 默认选中 | 第一个未拥有的配色 | **不变**（仍引导收集新配色） |
| `:467` 价格标签 | 已拥有时显示「已拥有」 | 始终显示价格；已有 n 件时追加「（已有 n）」 |
| `:470` 购买按钮置灰 | 已拥有 → 置灰（注释写明「置灰但可点，点了 toast 说明原因」） | 只受**解禁**与**货币**约束 |
| `Family.AllOwned` | 整族是否收集完 | 确认是否还有调用方，无则删 |

### 4.5 收纳栏语义重定义

`FurnitureSlotState` 里 `Placed` 的含义由「已经摆出去了」变成「**余量为 0**」：

```
余量 = OwnedCountOf(id) − 全部房间已摆放数（§4.2）
余量 > 0 → Available（可拖出）；余量 = 0 → Placed（置灰）
```

槽位上显示余量数字（如 `×2`）。【待确认】余量 0 时是否仍可点击弹购买弹窗：**默认允许**（正是玩家想再买一件的时机）。

## 5. 声望模型：只增不减

### 5.1 为什么改

声望的唯一去处是拒绝惩罚，唯一作用是家具解禁门槛（`IsFurnitureRevealed`）。两者叠加会**死锁**：条件类需求点名一件高门槛家具 → 声望不够买不到 → 只能拒绝 → 再扣声望 → 更买不到。钱不会锁死玩家（离场必留小费），但声望会。

访谈定案：**拒绝不再扣声望**，惩罚整体移除。

> **⚠ 2026-08-15 现状核实：死锁的一半已经被堵掉了，本节的动机要按下表理解。**
> 2026-08-14 的对话重构（第 6 题定案）已经把**两段超时**摘出了拒绝口径，所以现在只剩一条路还扣声望：
>
> | 路径 | 现状 | 代码位置 |
> |---|---|---|
> | 玩家在对话里显式选「拒绝」 | **仍扣**，按状态分两档（前台 −15 / 服务中 −30） | `DialogueFuncs["Reject"]` → `VisitorManager.Reject` → `SettleRefusal`（`:728`） |
> | 等搭话超时（FrontDesk） | 已不扣：直接 `Depart()`，也不播对话 | `VisitorManager.cs:218-220` |
> | 服务超时（Serving） | 已不扣：`SettleNeedResult(Mismatch, countAsServed:false)` → 播【需求反馈·失望】→ 转停留 | `:229-232`、`:253-256` |
> | 打烊清场 | 已不扣：`EndDay()` 里前台自动 `Depart()` | `:623-633` |
> | 【等待分配房间】 | 刻意不可拒绝（`CanReject` 只认 FrontDesk / Serving），不存在第三档 | `:335` |
>
> 因此本节要拆的是**主动拒绝那一档**，§5.2 的清单仍然全部适用；只是"死锁"的论证已经弱化——
> 现在玩家至少可以靠**放着不管让它超时**来免费脱身，代价只是拿不到四档奖励。

> **措辞提醒**：删完之后声望是**业务路径上**只增不减，不是绝对的。
> 对话事件 `AddReputation` 可以配负数（策划可见的公开入口），GM 面板还有「声望 -50」按钮
> （`GmAddReputation` 走独立路径、不发 `Feedback`）。这两个入口本次都不动。

### 5.2 改动清单

| 位置 | 改动 |
|---|---|
| `EconomyConfig.refuseReputationPenalty` / `serviceFailedReputationPenalty` | **删除** |
| `EconomyManager.RefuseGuestService()` / `RefuseServingGuest()` | **删除**（`:112` / `:123`，这两个方法现在只做扣声望）。**顺带记一笔现存不一致**：前者发了 `Feedback(ReputationLoss)`、后者没发，所以扣得更重的那一档反而没有音效反馈——一起删掉就不用管了 |
| `EconomyManager.RefuseReputationPenalty` / `ServiceFailedReputationPenalty` 两个只读属性 | **删除**（`:73` / `:76`）。⚠ 原文写「消费方是已退役的交付页按钮文案」**不准确**：真实消费方是 `VisitorManager.cs:734` 累加 `ReputationLost` 的那两行，**先删那里再删属性**，否则编译不过 |
| `VisitorManager.SettleRefusal`（`:728`） | ⚠ 原文写「简化为播【被拒绝】对话 → 离场」**已过时**：【被拒绝】分类已随对话重构整个删除（拒绝台词现在是【初次见面】/【等待接待】选项的子句），本方法根本不播对话。删掉两档分支后只剩 `RefusedCount++` + `Depart()`，**可以整个内联进 `Reject()`** |
| `VisitorDaySummary.ReputationLost` 及日结面板对应展示 | **删除**。⚠ 展示落点是 **`HouseUI/DayTransitionFx.cs:159`**，不是 `DaySettleOverlay`——后者已随 `a9d6c32`「结算讯息移到左上角」删除 |
| 音效 `ValueLose` 在拒绝处的触发 | 随之消失。但**「`EEconomyFeedback.ReputationLoss` 是否整个没有产生方」已核实：仍有，不要删枚举**——`AddReputation(负数)` 会发它（`EconomyManager.cs:148`），而对话事件 `AddReputation(-N)` 是策划可配的公开入口。`ValueLose` 音效映射（`SfxManager.cs:168` 的 default 分支）同样保留 |

### 5.3 已接受的后果：拒绝是零成本的

拒绝照拿基础小费、不扣声望 ⇒ 【拒绝】等于一个"跳过"按钮，玩家不想玩小游戏就可以拒掉。

> **2026-08-15 补**：这个后果其实**已经提前发生了**——超时早就不扣声望且照拿小费，所以"放着不管"
> 已经是一个零成本的跳过方式，只是慢一点。本包做的是把「主动拒绝」拉平到同一口径，
> 而不是新开一个免费出口。

访谈明确选择**接受**：改用**奖励驱动**而非惩罚驱动——完成服务多拿一份四档奖励（货币 + **声望**），而声望是家具解禁的唯一门槛，想买好家具就得好好服务。正向激励完整，只是没有负向惩罚，符合轻量休闲 AFK 的定位，也不会把新手卡死。

**记录在此是为了让后来者知道这是有意为之**，不要当成"漏配了惩罚"去补。

## 6. 进度与结局（demo 定位）

- 项目当前定位是**有限长度的 demo**：日程表排多少天就玩多少天。
- **日程表跑完最后一天之后**：出一个「感谢试玩」页，不再投放新访客。这取代了需求文档里那条占位默认值（原为「停止投放 + 打 Warning」）。
  - 触发时机【待确认】：**默认**在最后一天的【结束今天】日结之后弹出。
  - 形态【待确认】：**默认**复用现有整页路由（`HousePage` 派生，与 `ExitPage`/`GalleryPage` 同例），Prefab 缺失是报错不回退（§16.2）。
- **不做**：目标/任务系统（原待定 #1 的 Goals 随局内废弃已作废，不复活）、无限模式、日程循环、随机投放与随机需求。
- **存档（待定 #9）：先不做，接缝保留**。`Economy`/`Visitor`/`Dialogue`/家具布局四处的 `Capture`/`Restore` 维持无调用方状态，标题页「继续游戏/读取存档」维持占位。
  - ⚠ 维护税已知且已接受：**每次改数据结构都要顺手改这些没人调用的快照代码**（本文 §4.3 就改了 `EconomySaveData`），而且改错了编译器不报、测试不到。

## 7. 已知后果（已接受，不是待办）

可重复购买 + 装饰分给钱 ⇒ **「找出性价比最高的家具铺满房间」是刷小费的最优解**。访谈中明确选择**不处理**：房间格子数是硬上限，且铺满同款很丑、玩家自有审美约束。

若实测后想缓解，最小改动是「统计房间装饰分时按 id 去重」（同款只计一件），一行的事。
