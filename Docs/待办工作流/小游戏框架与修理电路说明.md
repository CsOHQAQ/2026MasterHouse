## 1. 一句话目标

建一套**零耦合的小游戏框架**（唯一入口是访客的小游戏类需求，唯一出口是一个 0~100 的分数），并把废弃的局内节点玩法**就地瘦身**为第一个小游戏「修理电路」。

## 2. 范围

| 做 | 不做 |
|---|---|
| 小游戏框架（契约 + 宿主 + `MinigameDef`） | 除修理电路外的其他小游戏（调制饮料、家务类等） |
| 修理电路：玩法逻辑 + UGUI 表现 + 交互 + 关卡编辑器 | 小游戏的存档（无限重开即重置，不需要） |
| `NodeSim` → `Minigame/Circuit` 的迁移与瘦身 | 家具 → 小游戏升级的读取通道（留启动参数位，本轮不接） |

## 3. 小游戏框架

### 3.1 依赖方向（这是整个框架的立身之本）

```
Visitor / Dialogue          ←─ 不认识小游戏
      │ StartMinigameAction（对话分支事件）
      ▼
MinigameOverlay（宿主）     ─→ 认识 IMinigame 与 MinigameDef
      │ Launch(level, onFinish, onAbort)
      ▼
具体小游戏（Circuit…）      ←─ **不认识任何 Manager**
```

小游戏**只认识两样东西**：`IMinigame` 接口，和自己的关卡类型。它不引用 `GameManager`/`VisitorManager`/`EconomyManager`/`HouseClockManager`/家具/经济中的任何一个。这条是硬约束，落地时全文检索一遍。

### 3.2 接口契约（`Minigame/IMinigame.cs`）

```csharp
public interface IMinigame
{
    /// <summary>启动一局。level 由宿主抽好；结束时必须调且只调一次 onFinish 或 onAbort。</summary>
    void Launch(MinigameLevelDef level, Action<int> onFinish, Action onAbort);
}

/// <summary>各小游戏关卡资产的共同基类（只为给关卡池一个类型约束，无字段）。</summary>
public abstract class MinigameLevelDef : ScriptableObject { }
```

- `onFinish(score)`：score 为 **0~100 的 int**，各小游戏自己定义怎么算。
- `onAbort()`：玩家中途退出，**不结算**——访客保持「服务中」，可以再点开重玩。
- 小游戏是 UGUI Prefab，根节点挂实现 `IMinigame` 的 MonoBehaviour。

### 3.3 时间：完全自治

小游戏**自己把 `deltaTime` 折算成自己的步长**（需要的话），与全局 tick 零关系。理由：小游戏期间营业闸门是关的，跟着全局心跳走会被一起冻住；而且自治才能兑现"零耦合"。

小游戏整体属 **View 层豁免区**（§16.4）：允许 `Time.deltaTime`、允许无种子 `Random`——它的结果由玩家操作决定，不是确定性业务推演。**唯一的例外是关卡抽取**（§3.5），那个必须确定性。

> 修理电路实际上**一拍都不需要**：供电判定是纯函数，玩家每次改动后重算一次即可（§4.2）。自治时间是框架能力，不是每个小游戏都得用。

### 3.4 宿主（`Minigame/MinigameOverlay.cs`）

`MinigameOverlay : IHouseOverlay`，压进 `HouseUIManager` 的叠加层栈，与 `DialogueOverlay` 同例（那个也是全屏的）。职责：

1. 关营业闸门：`EClockStopReason` 新增 `Minigame`，**计入 `IsWorldFrozen`**（与交付页当初的处置同口径）。
2. 按 `MinigameDef.prefab` 实例化，取其 `IMinigame`。
3. 抽关卡（§3.5）并 `Launch`。
4. 接 `onFinish(score)` → 查 `MinigameDef` 的阈值定档 → 调 `VisitorManager.CompleteNeed(instanceId, satisfaction)`；接 `onAbort()` → 只关页面。
5. 销毁实例、开闸门、退栈。

**退栈顺序照抄交付页的教训**：`CompleteNeed` 内部会同步压入【完成服务】对话层，所以必须**先弹栈关小游戏页、再调业务**，否则 `PopOverlay` 弹掉的会是对话框。两步在同一调用栈内完成，tick 插不进来。

ESC / 遮罩点击 = `onAbort()`。

### 3.5 关卡抽取：锁定同一张

```
关卡 = 池[ Hash(runSeed, 访客实例Id, 需求Id) % 池长度 ]
```

同一位访客反复进出**恒定抽到同一张**——"重开"是磨同一关，而不是刷关卡（否则理性玩家会反复退出直到抽到最好做的那张）。与项目现有的对话组选取、原交付预览是同一套派生种子思路，读档也不刷。

`DeterministicRng.Hash` 现成可用。

### 3.6 MinigameDef（`Minigame/MinigameDef.cs`）

```csharp
[CreateAssetMenu(menuName = "MasterHouse/小游戏定义", fileName = "Minigame_")]
public sealed class MinigameDef : ScriptableObject
{
    public string minigameId;              // 稳定键
    public string displayName;
    public GameObject prefab;              // 根节点须挂 IMinigame 实现
    public List<MinigameLevelDef> levels;  // 关卡池，全池随机（§3.5）

    [Header("分数 → 满意度（升序阈值，含下界）")]
    public int plainMin = 1;       // ≥ 此值为「一般」，低于则「不对味」
    public int satisfiedMin = 60;
    public int perfectMin = 100;
}
```

- **Prefab 用强类型引用**而不是 Resources 路径字符串：拖拽即可、改名不断、Unity 自动处理依赖。
- **难度不做单独抽象**：要区分难度就多做一个 `MinigameDef`（同一个 prefab、不同关卡池）。这是用资产模拟档位，符合§15.3。
- `MinigameNeedDef` 加一个字段 `public MinigameDef minigame;`（现在是空壳，见 `Visitor/MinigameNeedDef.cs`）。

### 3.7 接入需求侧

`StartMinigameAction` 读 `ctx.Visitor.Need as MinigameNeedDef` → 取其 `minigame` → `MinigameOverlay.Request(...)`。取不到时报错 + Toast，**不改变业务状态**（对话铁律 1）——访客仍在「服务中」，玩家可以再点开重试。

⚠ **它只登记意图，不当场打开页面**。本事件在 `DialogueManager.ChooseOption` 内执行，此时对话层还在栈顶且仍在播；当场 `PushOverlay` 的话，紧接着的 `Finish() → PlaybackEnded → DialogueOverlay.CloseFromPlaybackEnded → PopOverlay` 弹掉的会是**小游戏层**而不是对话层。

真正打开由 `HubPage.OnDialogueEnded` 在 `DialogueOverlay.CloseFromPlaybackEnded()` **之后**调 `MinigameOverlay.ConsumePending(UI)`。ESC 中断路径也走得到（`Interrupt → AfterPlayback → PlaybackEnded`），与"已执行的事件不回滚"一致。离开 Hub 页时 `DiscardPending()` 丢弃未消化的请求。

这条与 §3.4 的出口侧退栈顺序是同一类坑的两面，都已在 `MinigameOverlay` 的类注释里写明。

## 4. 修理电路

> ⚠ **§4.2 与 §4.7 已于 2026-08-13 落地访谈整体改写。** 原「份额制」模型（一条链接 = 一份电、`OutputCount` 表示引出几条线）**已作废**，下文是现行模型。改写的起因是一条更简单的接线规则：一个 Pin 只接一条线。

### 4.1 玩法一句话

电源提供的电是**有限电量**，电池要求**具体数值**，玩家用有限的导线与中转件把电分配到尽可能多的电池上。

### 4.2 电力模型（电量制，无时间维度）

三条规则就是全部：

- **① 一个 Pin 至多接一条线**，链接本身**没有载量上限**。
  电源的每个输出 Pin 按自己的 `PinDef.MaxRate` 送出电量；电源可配多个输出 Pin，总供电 = 各输出 Pin 的 `MaxRate` 之和。
  `MaxRate` **只对电源有效**，中转件一律不限流。（`ResourceNodeDef.OutputCount` 因此失去意义，字段保留但标注已弃用。）

- **② 中转件按 `PinDef.PinGroup` 分组**，同组内按方向分进出：

  ```
  每个输出口的电量 = floor( 组内输入之和 / 组内输出口总数 )
  ```

  三种件型全是这条公式的特例，共用同一个 `TransitNodeDef` 类，**加件型 = 加资产，不加代码**：

  | 件型 | 组的形状 | 公式结果 |
  |---|---|---|
  | 十字件 | 两个组，各 1 进 1 出（方向留「同步」，运行时定向） | `floor(x/1) = x`，直通 |
  | 分流器 | 一个组，1 进 N 出 | 平分 |
  | 合流器 | 一个组，N 进 1 出 | 求和 |

  分母是**输出口总数**，不是已接线的口数——没接线的口那一份会浪费掉；整除余数同样蒸发。这给了玩家凑整除数的动机。
  本轮只做 1:N 与 N:1；M:N 公式照样成立但未验收，编辑器给警告。

- **③ 电池可配多个输入 Pin**，收到的电量 = 各输入 Pin 上链接携带电量之和，再逐条判定：
  - 收到量 == `RequiredAmount` → 点亮
  - 收到量 < `RequiredAmount` → 不亮
  - 收到量 > `RequiredAmount` → 看 `AllowExcess`：允许则点亮，否则**不亮**

  `AllowExcess = false` 是核心难度旋钮：玩法从"尽量多连"变成"**精确分配**"。
  多输入口意味着电池自己就能合流，**合流器不是通关必需品**，而是省导线格数的优化件。

**判定是纯函数**（`CircuitSolver`）：从各电源沿链接记忆化传播 → 汇总各电池收到的电量 → 逐个判定。玩家每次增删线/摆件后重算一次，**不需要 tick、不需要动画时序**。

**成环在建线时拒绝**（`LinkManager.TryCreateLink` → `CircuitSolver.WouldCreateCycle`）：合流器输出绕回自己的输入会让"输出 = 输入之和"变成自指方程，纯函数求解器无解。图的顶点是 **(节点, 分组)** 而不是节点——十字件的两个分组互不连通，按节点粒度检测会把「两条线各走一组的正常交叉」误判成环，那正好废掉十字件唯一的用途。

### 4.3 两个资源约束（关卡资产里的难度旋钮）

| 约束 | 落点 | 手感 |
|---|---|---|
| **导线总格数上限** | `LevelDef` 新增 `MaxLinkCells`（0 = 不限） | 描格时预算耗尽即**停住不延伸**，与撞墙同一手感（不作废本次绘制，玩家可以退回重画）。删线退还预算 |
| **中转件数量上限** | 沿用现有 `BuildableNodes` 的 `MaxCount` | 已有机制，`CanBuild` 已按它校验 |

导线预算的统计口径**沿用已有实现**：`Σ link.PathCells.Count`，落地为 `LevelData.UsedLinkCells`（原实现在已删除的 `DebugPanel.cs:295-304`）。描格途中还要额外算上当前正在画的格数。

UI 常驻显示 `导线 34/50`、`中转件 2/3`，剩余为 0 时数字变红。

### 4.4 计分

```
分数 = 点亮的电池数 / 电池总数 × 100   （四舍五入）
```

- **按节点个数**，不按需求量加权，不给部分分（"点亮"是二元的，与 `AllowExcess` 的二元语义一致）。
- **线长与中转件用量不参与计分**——它们是准入约束，不是评分项。
- 粒度提醒写进关卡编辑器的提示：**2 个电池的关卡只能出 0/50/100 三种分数**，想要细梯度就多放电池。

### 4.5 完成与放弃

- 页面上常驻【完成】按钮 + `已点亮 2/3`，**随时可点**，按当前占比结算 → `onFinish(score)`。
- 【放弃】/ ESC / 点遮罩 → `onAbort()`，访客保持「服务中」，可再次点开重玩，**局面重置**（不保留上次布线）。
- 没有失败条件，没有时间/步数限制。

### 4.6 操作集合（全鼠标）

| 操作 | 行为 |
|---|---|
| 从 Pin 按住拖动 | **描格**画线，手感规则原样沿用：撞到非法格停住不延伸、鼠标退回已画格则截断、斜向自动补直角 |
| 松手在合法目标 Pin 的接口格 | 成线；否则整次作废（静默） |
| 右键短击线 | 删除该线（高频操作，免选中） |
| 从件库拖出中转件 / 点选后落子 | 摆放，幽灵预览绿/红 |
| 拖动已摆的中转件 | 移动，**附着导线直接删除并退还预算**（不保留断线态；小游戏可无限重画，留个半死不活的对象不划算） |
| 选中 + Delete / 右键 | 删除已摆的中转件（附着导线同样删除退还） |

电源与电池是关卡预置的**题面**，不可移动、不可删除。

### 4.7 中转件（三种件型，同一个类）

件型完全由资产里 Pin 的**分组与方向**决定，`TransitNodeDef` 是空壳类：

| 件型 | 配法 | 作用 |
|---|---|---|
| **十字件** | 两个组，每组两个口，方向都留「同步」（运行时定向） | 转向与交叉——线不能共格、不能穿节点，两条线要交叉就只能走它 |
| **分流器** | 一个组，1 个输入口 + N 个输出口 | 把一份电平分成 N 份（向下取整） |
| **合流器** | 一个组，N 个输入口 + 1 个输出口 | 把多路电合成一路 |

「同步」方向只在**恰好两个口的组**上成立（十字件那种 1 进 1 出）——三口以上分不清谁是那个"1"，所以分流/合流必须配死进出，编辑器会校验。

分组号与 Pin 下标**完全解耦**（不再是旧版"互指的配对索引"），所以删一个 Pin 不必连带删伙伴、也不用重映射任何索引。

**非法临时态一并退役**：`NodeData.IsIllegal`／`LevelData.HasIllegalObjects` 是给「有存档的产线」设计的（移动节点落点冲突 → 冻结对象 + 禁止存档）。小游戏无存档、且摆件有幽灵预览绿/红，落点非法时 `MoveNode` 直接返回 false 什么都不做，不需要中间态。

### 5.3 逻辑替换

**删**：三阶段 tick 流水线、投递/取货、持货槽、节拍、在途计时、背压、仲裁与轮询指针、`ConditionState` 的滑动窗口、家具效果产出。

**新写**：`CircuitSolver`（纯函数，无状态）——从各电源沿链接记忆化传播电量，汇总各电池收到的电量，按 §4.2 判定点亮；另含计分 `Score` 与建线用的成环检测 `WouldCreateCycle`。**调用点已内建**：`LevelManager` 与 `LinkManager` 的每个改动布局的公开方法都在收尾时先 `Solve` 再广播事件，订阅方读到的一定是算好的结果，不必自己记得调。

**原样保留**：`LinkManager.ValidatePlayerPath`（每格 ∈ 画布 ∧ 未占用、4 向连续、不自交、首尾接在两端 Pin 的外侧接口格、必要时整条反转）——**这是本次迁移最值钱的一块，也是最容易写错的一块，不要重写**。占格索引、`GridGroup.CellsAt`、`Direction4` 同理。

### 5.4 编辑器

- `LevelCanvas`（画布绘制 + 点击摆预置节点 + 按类型着色 + FitTo）、`NodeShapeCanvas`（画形状 + 摆 Pin）、`CanvasDrawUtil`——**三个绘制工具一行不改**（类名不变就不用动签名）。
- 两个窗口本体：删掉家具绑定、产出、配方、暂存的绘制区块；`DrawAutoFields` 的 SerializedObject 自动绘制保留（加字段零维护，`MaxLinkCells`/`OutputCount`/`AllowExcess` 会自动出现）。
- 校验规则改写：删掉条件节点/产出相关的旧规则，新增——电源总份额 < 电池总需求（**警告**：本关不可能全亮）、`MaxLinkCells` 小到显然连不通（警告）、画布为空/无电源/无电池（报错）、中转件未配配对 Pin（报错）。

### 5.5 改名（可选，第 6 步）

`LevelDef → CircuitLevelDef` 之类。**必须同步改文件名、`.meta` 不动**。嫌麻烦可以不改——在 `Minigame/Circuit/` 目录下叫 `LevelDef` 也说得通。
