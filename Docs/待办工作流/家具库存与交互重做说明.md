## 1. 一句话目标

把家具从「买一件、每房摆一件、摆完没去处」的半成品，做成**真正的库存系统**——有几件摆几件、同房可重复、商店不限量、支持半价回收；同时修掉家具热点阻挡相机拖拽的老问题，并让装饰分与声望这两个数值第一次真正生效。

## 3. 现状诊断（实测数据，2026-08-15）

### 3.1 家具热点挡住了相机拖拽

`HubSceneBinder.BuildHotspots()`（`:339-378`）给每件已摆放家具建一个透明 `Button`（`:351-358`）。而相机平移的起手判定是：

```csharp
// HubSceneBinder.cs:136
if (Input.GetMouseButtonDown(0) && insideScene && !IsPointerOverBlockingUI())
```

`IsPointerOverBlockingUI()`（`:288`）就是 `EventSystem.IsPointerOverGameObject()`，热点是 raycast target ⇒ **在家具上按下就完全无法平移相机**，连「缩小后点一下聚焦房间」（`:148`）也一起失效（`pressValid` 根本没置起来）。

uGUI 的 `Button` 不带拖拽阈值，拖完在同一热点上松手照样触发 `onClick`，所以现在「想拖动画面」的操作会变成「打开家具图鉴面板」。

访客拖拽**不受影响**：`VisitorStage` 建在热点层之后（`:77` vs `:79`），是更靠后的兄弟节点，射线先命中演员。

### 3.2 点家具不知道点的是哪件

热点的 `onClick` 只是 `page.OpenPanel(EHousePanel.Device)`（`:358`），不带参数；面板自己 `selectedRoom = page.RoomIndex; selectedIndex = 0`（`DevicePanelBinder.cs:20-21`），于是点沙发和点台灯打开的是同一个东西。

`BindOverlay()` 里还挂着一个**硬编码的假热点**（`:399-402`），标题按房间下标写死「手冲咖啡台 / 旧书检索机 / 黑胶唱机」，与真实摆放毫无关系，是原型残留。

### 3.3 总览态的「当前房间」恒为卧室

`HubWorldGrid.RoomAt()`（`:30-34`）的边界判定是 `>=`：

```csharp
var col = world01.x >= .5f ? 1 : 0;
return (world01.y >= .5f ? 0 : 2) + col;
```

缩到 zoom 0.5 时，世界尺寸恰等于视口，`ClampCamera` 把平移钳成 0，视口中心正好落在世界正中心 `(0.5, 0.5)` ⇒ **`RoomAt` 恒返回 1（卧室）**。导航高亮、场景说明卡、以及「家具摆放」进哪间房全跟着跳。本轮把双击缩回总览做成常用手势后，这个既有小毛病会变成每次都撞上。

### 3.4 所有权没有数量概念

`EconomyData.OwnedFurniture` 是 `HashSet<string>`（`:54`），每种最多一件；`TryPurchaseFurniture`（`EconomyManager.cs:168`）第一道门就是「已拥有 → `AlreadyOwned`」。

而 `FurnitureRoomController.IsPlaced(id)`（`:421`）**只遍历当前打开房间的 `items`**，不跨房间 ⇒ 「每种只能拥有一件」这条规则在四宫格改造后早已形同虚设：同一张沙发可以在四个房间各摆一份。

### 3.5 没有任何家具带桌面格（已修）

`家具表.csv` 的「桌面格启用」原本 121 行全是「否」，于是 **32 件桌面家具（台灯 6 / 仙人掌灯 5 / 熔岩灯 8 / 球形摆件 9 / 月牙水族箱 4）根本摆不出来**——拖出去只会 toast「需要先摆放带桌面格的家具（如茶几）」，可它们在商店里照卖不误。

已于本轮配置修复：`round_table` 八行开启桌面格，偏移 X 从 50 改为 4（3 列 × 64 = 192，居中于圆桌 200 显示宽）。

### 3.6 声望毫无作用（已修）

商店表原本 121 行的「解禁声望」全是 0 ⇒ `IsFurnitureRevealed` 恒为 true，商城一张「？」卡都不会出现。而解禁是声望的唯一作用，所以声望此前是纯装饰数字。已于本轮配置修复（见 §8）。

### 3.7 房间与家具的关系是「按 id 分桶 + 按需拉取」

不是主动注册。房间（`FurnitureRoomEntry`）是只读 Def，不持有运行时摆放：

```
摆放/收纳/翻转/关闭模式
  └─ FurnitureRoomController.SaveState()        :914   当前房间 items → sessions[room.id]
        └─ CaptureSessionPlacements(roomId)     :823   对 active 房间先 SaveState()；null = 从未编辑过
              └─ FurniturePlacementQuery               业务层唯一入口（View 层 static 字典禁止直读，§11.4）
                   FurnitureIdsIn(roomIndex)    :21
                   RoomHasAny(roomIndex, ids)   :39
```

三个局限，新功能必须知道：

1. 返回的是 **id 列表不是实例**，同款多件会重复出现多次（本轮之后会变常见）。
2. 唯一带位置的查询是 `FurnitureSceneComposer.GetPlacedFurniture(roomIndex)`（`:145`），返回 entry + 归一化视口矩形（Hub 热点用它建）。
3. `CaptureSessionPlacements` 对**正在打开的房间有副作用**（触发 `SaveState()`），每帧/每槽位调用的热路径必须绕开它、直接读 `sessions`。

## 4. 家具交互：点击与拖拽分离

### 4.1 判定方式

**热点不再挂 `Button`**，只保留 `raycastTarget = true` 供悬停提示卡使用；`IsPointerOverBlockingUI()` 排除热点层（靠一个 marker 组件或 `transform.parent == hotspotRoot` 识别）。点击与拖拽的裁决统一收到相机层：

```
松手时：位移 < 9px（sqrMagnitude < 81，复用 HubSceneBinder.cs:148 现有阈值）
  ├─ 命中家具热点 → 打开该件家具的详情
  └─ 未命中（空地）→ 走双击判定
位移 ≥ 9px → 视为拖拽，只平移相机，不触发任何点击
```

一处判定，平移 / 双击 / 开详情三处复用；顺带修好「在家具上按下无法聚焦房间」。

### 4.2 家具上只认单击

**双击放大只在空地生效。** 家具是「物件」，点它看详情；地板是「场景」，双击它推镜。两条分支互斥、无延迟、无待定计时器状态。

这条是为了避开一个死结：双击的第一击若落在家具上，单击已经把详情面板压栈了，第二击就落到面板上，双击必然失效。

代价：家具密集的房间里玩家得找块空地双击。已接受。

### 4.3 双击语义

| 当前缩放 | 双击行为 |
|---|---|
| `camZoom < 1`（总览态） | 推镜到双击处所在房间满屏（复用现有 `FocusRoom`，`targetZoom = Mathf.Max(1f, camZoom)`） |
| `camZoom >= 1`（房间态） | 缩回 0.5 总览 |

zoom 0.5 时世界尺寸恰等于视口，`ClampCamera` 自动把平移钳成 0，缩回不需要额外算位置。

原来的「缩小态单击聚焦房间」（`:148`）**删除**，由双击取代。

### 4.4 总览态不更新当前房间

`DetectCurrentRoom()` 在 `camZoom < 1` 时直接 `return`，沿用缩回前的房间（§3.3）。总览态本来就没有「当前房间」这个概念，沿用上一个是最小意外。双击选房时 zoom 推回 1，会正常更新。

### 4.5 单击家具 → 定位到那一件

`PanelHost.Open` 透传一个可选的 `(roomIndex, furnitureId)`，`DevicePanelBinder.Bind` 收下并把 `selectedRoom` / `selectedIndex` 定到匹配项。

**必须传 id 不传下标**：热点来自 `FurnitureSceneComposer.Collect`（先地面后桌面），面板列表来自 `FurniturePlacementQuery.FurnitureIdsIn`（原始顺序），两者排序不同，传下标会错位。

**必须同时传 roomIndex**：总览态下玩家点的可能是别的房间的家具，而面板现在是拿 `page.RoomIndex` 当选中房间的。

同房间有多件同款时按 id 匹配第一件即可——它们本来就是同一件东西。

### 4.6 删除假热点

`BindOverlay()` 的 `hotspotTitle` / `hotspotButton`（`:399-402`）删除，Prefab 里的节点隐藏即可，不动布局。

## 5. 库存系统

### 5.1 核心语义

```
余量 = 拥有数 − 全部房间已摆放数
```

- **同一房间可以摆多件同款**。买 3 张椅子，可以一间房摆 3 张，也可以三间房各一张。
- **商店不限购买数量、无上限**。房间格子数本来就是硬约束，囤着不摆没有副作用，加数字上限只会多一处规则要维护。
- 已摆放数的统计口径：**当前打开的房间取实时 `items`，其余房间取 `sessions` 会话布局，未编辑过的回落 `room.initialPlacements`**。当前房间必须读 `items` 而不是 `sessions`，因为 `MoveItem`（`:407`）不调 `SaveState`。

### 5.2 数据结构

| 位置 | 改动 |
|---|---|
| `EconomyData.OwnedFurniture` | `HashSet<string>` → `Dictionary<string, int>`（id → 拥有数）。注释写明「只做键查询与计数；如需遍历展示须先按 id 排序（§11.2）」 |
| `EconomyManager.IsFurnitureOwned(id)` | 签名不变，改为 `=> OwnedCountOf(id) > 0`，所有既有调用方零改动 |
| 新增 `OwnedCountOf(id)` | `TryGetValue`，缺省 0 |
| `TryPurchaseFurniture` | 删掉 `AlreadyOwned` 分支；保留一道 `PriceOf(entry) <= 0 → NotForSale`（防漏配：不在商店表里的家具会被 `PriceOf` 兑成 0，不拦就是免费无限买）；解禁与货币两道门不变；成功则 `OwnedFurniture[id] = OwnedCountOf(id) + 1` |
| `FurniturePurchaseResult` | 保留 `AlreadyOwned` 占位但不再返回（注释标注已废弃）；**新增 `NotForSale`**。注意把各处 `switch` 的 `default` 文案从「已拥有该家具」改掉，否则会给出误导提示 |
| 新增 `SellFurniture(id)` | 见 §5.5 |
| `EconomySaveData.ownedFurniture` | 改为 `List<OwnedFurnitureSaveData>{ id, count }`。**不要**用「重复 N 次的 id 列表」，那是管道分隔字符串的近亲。序列化前按 id `string.CompareOrdinal` 排序（§11.2） |
| `AddFreeFurniture()` | **整个删除**，由初始携带取代（§5.3） |
| `ComputeInitialFurnitureDecor()` | **整个删除**。它只统计 `rooms[0]`、与 `SyncDecorationFromSession` 的全房间口径不一致；新游戏路径上会被随后的 `ResetSession()` 覆盖（`TitlePage.cs:159-161` 的顺序），本来就是死值 |

### 5.3 初始拥有 = 初始摆放数 + 初始携带列表

**初始摆放保留**（`家具房间表.csv` 的 15 条不动），玩家自动免费拥有它们。

```
初始拥有数(id) = 全部房间 initialPlacements 里该 id 的出现次数（代码自动统计）
               + EconomyConfig.startingFurniture 里配的数量
```

这条等式是硬约束：**初始摆放的家具玩家必须拥有，否则余量算出来是负数**。让代码自动统计而不是要求策划手配，好处是余量永不为负，且「携带」的语义干净——它就是「开局收纳栏里有几件可摆」，策划不用心算减法。携带列表留空就是「只拥有场上摆着的那些」。

`EconomyConfig` 新增：

```csharp
[Serializable] public sealed class StartingFurniture { public string furnitureId; public int count = 1; }
[Tooltip("开局额外携带的家具（收纳栏里可直接摆的份数）。场上初始摆放的家具会自动计入拥有数，不必在这里重复配")]
public List<StartingFurniture> startingFurniture = new List<StartingFurniture>();
```

`furnitureId` 用现有的 `FurnitureIdAttribute` 下拉选，避免拼错。

**建议起手清单**（都在 0 声望档，覆盖地面/壁挂两个页签）：

| id | 份数 |
|---|---|
| `potted_plant_01` | 2 |
| `vintage_square_clock_02` | 2 |
| `hanging_plant_01` | 2 |
| `landscape_poster_02` | 1 |
| `round_table_01` | 1 |

开局收纳栏 8 件、分属 5 族。桌面页签因无内容会自动隐藏（`EnsureTabAvailable` + `hasAny` 已处理）。数量随策划调。

### 5.4 桌面家具的宿主引用改为坐标键

**这是同房可重复的硬前置。** 现在宿主是按家具 id 存的：

```csharp
// SaveState :936     hostFurnitureId = host.Entry.id
// RestoreState :906  foreach (var item in items.Values) if (item.Entry.id == placement.hostFurnitureId) { host = item; break; }
```

同房间摆两张一样的茶几时，重进房间后**桌上所有东西会挤到第一张上**，第二张的桌面格空着，挤不下的还会被 `FootprintFree` 丢弃——家具凭空消失级别的 bug。`FurnitureSceneComposer.HostedAnchor`（`:216-223`）有同一个问题。

改法：`FurniturePlacementConfig` 的 `hostFurnitureId` → **`hostGridId` + `hostCol` + `hostRow`**（宿主基础家具的落位坐标）。坐标键稳定且唯一——一个网格的一个格子上只能有一件基础家具。判据 `IsOnHost` 与匹配 `OccupiesBaseCell` 都挂在这个类上，消费方不再各写一遍字符串判空。

`RestoreState` 先摆基础家具，再摆桌面家具时按 `(gridId, col, row)` 查宿主实例。`FurnitureSceneComposer.HostedAnchor` 同步改（那是锚点数学的第二份实现，§16.7 已知技术债，改一边必须同步另一边）。

**CSV 与 Excel 一个字都不改**（2026-08-15 访谈定案）：策划照旧在「宿主家具id」列填家具 id，由 `FurnitureCsvImporter.ResolveHostReferences` 在**导表期**翻译成坐标——填坐标对策划反直觉，而运行时又必须无歧义，翻译放在导表器是两全。

- 解析在**全表读完之后**做（宿主行可能排在被托管行之后，边读边查会漏）
- 同房间存在多个同 id 候选时 **LogError 并丢弃该行**，不静默取第一个——那正是坐标要解决的歧义，静默取第一个等于把 bug 从运行时挪到导表期。策划想在两张同款桌上放不同东西，换个配色即可
- 导出侧 `HostFurnitureIdOf` 做反向翻译，保证 asset → CSV → asset 往返一致
- 运行时（玩家自己摆的会话布局）完全不受这条配置层限制，走的是纯坐标

**零数据迁移**：实测 15 条初始摆放的「宿主家具id」列**全部为空**，没有一件桌面家具。

### 5.5 半价回收

| 项 | 决定 |
|---|---|
| 比例 | `EconomyConfig.sellbackPercent = 50`（**整数百分比**，回收额 = `PriceOf(entry) * percent / 100`，整数除法，§11.3）。实测全部族价均为偶数，整除无损 |

### 5.6 收纳栏语义重定义

`FurnitureSlotState.Placed` 由「已经摆出去了」变成「**余量为 0**」：

```

```

- **删除 `FurnitureRoomController.IsPlaced(string)`**，由 `RemainingOf(id)` 取代。
- 余量数字**复用现有的 `slot.placedLabel` 节点**（`OutGameFurnitureSlotView.placedLabel`），零 Prefab 改动。
- 余量 0 时点击槽位 → 弹购买弹窗（`装饰分与经济循环说明.md` §9 待确认 #3 的默认值）。`AddFreeFurniture` 退役后不再有 price ≤ 0 的成员，非卖品特例自然消失。

- `Dictionary<string,int> placedCounts` + `bool placedCountsDirty` 脏标记，一次重建 O(全房间摆放数)。
- 重建时**直接读 `sessions` 私有字段，绕开 `CaptureSessionPlacements`**（后者对 active 房间会触发 `SaveState()`）。控制器本来就是 `sessions` 的所有者，不算越权——§11.4 约束的是业务层。
- 失效点：`PlaceItem` / `StoreItem` / `RestoreState` 末尾 / `Init`；静态的 `RestoreSessionPlacements` / `ResetSession` 里补 `if (active != null) active.placedCountsDirty = true;`。`MoveItem` 不需要（同房内移动不改计数），购买/出售也不需要（`OwnedCountOf` 实时读）。

## 6. 经济数值

### 6.1 装饰分按房间生效

```
离场小费 = guestLeaveTip                              （所有业务访客，含被拒绝与超时流失的）
         + 房间装饰分 / decorScorePerTip              （仅完成需求的访客，整数除法）
```

- `decorScorePerTip` 新增到 `EconomyConfig`，取 **2**。语义是「多少装饰分换 1 货币」，与 `装饰分与经济循环说明.md` §3.2 的 `tipPerDecorScore`（每点加多少钱）**方向相反**，字段名一并改掉避免误读。
- **加成只给完成服务的客人**，基础小费仍是所有离场都给（防没钱死锁的保证不变）。

**为什么要收紧**（原文 §3.2 说「线性、无封顶，房间格子数本身就是硬上限」，但严重低估了格子数）：

| 项 | 实测 |
|---|---|
| 单房间地面网格 | 306~312 格 |
| 单房间壁挂网格 | 765~780 格 |
| 复古方钟 | 2×2 格、装饰分 12 ⇒ 光壁挂就能塞 195 件 = 2340 分 |
| 单房间理论上限 | **约 3252**（未计桌面格） |

按原文的 `+装饰分 × 1`，铺满时单人小费 3570，是服务奖励（320）的 11 倍；而离场小费**每位访客都给**、服务奖励只有完成才给 ⇒「装修好 + 全部拒绝」成为纯收益最优解，正是原文 §5.3 担心的「拒绝变成零成本跳过按钮」的放大版，且拒绝的声望惩罚本轮还要删掉。

收紧后的量级（摆 10 件 ≈ 200 分，一天完成 3 位服务、奖励合计 960）：

| 装修程度 | 房间装饰分 | 单人加成 | 占当天服务奖励 |
|---|---|---|---|
| 空房 | 0 | +0 | 0 |
| 摆 10 件 | ~200 | +100 | 31% |
| 3 天能买到的极限（约 40 件） | ~720 | +360 | — |
| 铺满 | ~3250 | +1625 | — |

选 2 而不是更保守的 3 或 5，是因为文档 §3.4 那条约束：因果链**感知不到就等于不存在**。摆 10 件看到 +100、约占当天收入三成，玩家能明确意识到「装修真的在赚钱」。

## 7. 本轮不做：收纳栏换色组折叠

`家具族体系说明.md` §4.3 的「一族一槽位 + 内嵌色块条」**本轮不做**。验证结论：

**族表已经不是障碍了。** 访谈期间（2026-08-15）族体系的数据层已并行落地：`FurnitureFamilyTable` + `FurnitureEntry.familyId` + 四表导表管线，族级属性在导表时展开进每一行。所以折叠要用的 `entry.familyId` 是现成的，连 `StoreOverlay.FamilyKey` 的前缀猜法都可以一并退役。

（作为参照，前缀猜法当时也是可靠的：实测 121 行 id **全部**符合 `<族>_<两位数字>`，零例外，聚出 15 族。）表面类型 121 行全是单值（地面 50 / 壁挂 39 / 桌面 32），**族不跨页签**，折叠实现不用处理「一个族的成员分散在不同页签」。折叠后地面 7 族 / 桌面 5 族 / 壁挂 3 族，每页签一页 12 槽绰绰有余，翻页按钮可以直接不显示。

**但收益是后期的。** 收纳栏只列已拥有的家具（`EntriesOf` 过滤未拥有），开局那 15 件初始摆放 + 建议携带清单只分属 9 族，本来就一页装得下，折不折叠看不出差别。翻页痛点要到玩家买了几十件才出现（全买 121 件时地面页签 50 槽 = 5 页，折叠后 7 个 = 1 页）。

**而形态还没定。** 槽位模板只有 104×122（缩略图 84×76 + 名称条 + 角标），塞色块条一行最多约 4 个，而 `hanging_plant` 有 22 个配色。族表文档 §6 待确认 #2 给的默认值「横向滚动」在 104px 宽里基本不可用，需要重新设计（候选：槽位展示当前配色 + 单击弹配色浮层，与 §4.1 的位移阈值判定同构）。

结论：等玩家真买到几十件、痛点实际出现时再做，届时族表大概率已落地，`FamilyKey(id)` → `entry.familyId` 一起换，只改一次。

1. **拒绝是零成本的**（§6.4 已详述）。有意为之。
2. **开局四个房间不是空的**，但收纳栏只有携带清单那几件——想大改布局得先去商店买。初始现金 2480，商店 121 件均价 100~400，够买十几件。
3. **免费家具不复存在**。`AddFreeFurniture` 退役后，price ≤ 0 只剩「漏配」一种含义，被 `NotForSale` 挡下。
4. **`装饰分与经济循环说明.md` §12 的一条验收项不严格成立**：「服务奖励 + 客人小费 = 当日货币增量」——对话事件的 `AddCurrency` 与 GM 加币都不进 `VisitorDaySummary`。验收时注明「当天没有对话货币事件」的前提。
5. **存档仍然不做**（待定 #9）。`Economy` / `Visitor` / `Dialogue` / 家具布局四处的 `Capture` / `Restore` 维持无调用方。⚠ 维护税已知且已接受：本文 §5.2 就改了 `EconomySaveData`，而改错了编译器不报、测试不到。Review 时专门对着 `Restore` 看一眼。
6. **家具模式开着时时钟照走**（`OpenFurnitureMode` 不退页），所以 `Depart` 可能在 `active != null` 时经 `DecorationScoreOf → CaptureSessionPlacements` 触发 `active.SaveState()`。行为是安全的（只写自己的 `sessions`，无广播、不动 `Data.Instances`），但这是「业务 tick 触发 View 层写状态」，在 `Depart` 与 `CaptureSessionPlacements` 两处各留一句注释说明是已知且刻意的。同款先例已有（条件类需求的 `RoomHasAny`）。
7. **锚点数学仍是双实现**（`FurnitureRoomController.AnchorOf` 与 `FurnitureSceneComposer.BaseAnchor`），§16.7 已记为二轮技术债。本轮改宿主引用要**同步改两边**，否则家具模式里和 Hub 上会错位。
