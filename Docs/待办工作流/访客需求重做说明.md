## 1. 一句话目标

访客的需求**不再要求交付物品**，改为两类：**条件类**（所住房间里要有指定家具之一，验收走对话分支条件）与**小游戏类**（玩一局小游戏，按分数定满意度，本包只占位）。随之整条 Item 链（物品/仓库/交付页/标签森林/需求造句器）退役。

## 2. 背景：为什么推翻

局内节点玩法（`NodeSim`）已决定**全线废弃**，轻量化重构为一套 UI 小游戏。局内是 `ItemDef` 的唯一产地（`LevelDef.Outputs` → `PlayerCargo`），而 `PlayerCargo` 的唯一出口是交付页——产地与出口同时失效，Item 体系整体失去存在理由。

同时家具不再有「修好与否」一说：**摆在场上即发挥作用**（装饰分），关卡不再是家具的入口。

## 3. 现状差距（开工前必读）

| 目标 | 现状 | 处置 |
|---|---|---|
| 需求 = 条件类 / 小游戏类 | 需求 = 一组 `TagDef` + 是否必要 | `VisitorNeed` 退役，重建为 `NeedDef` 资产体系（§4.1） |
| 一人一条需求 | `needCountMin/Max` 抽 1~2 条 | 改为单条 |
| 需求写死在日程表 | 种族权重表 + 派生种子 roll | `RollNeeds()`、`needTagWeights` 全部退役（§4.2） |
| 房间是业务判定依据 | `VisitorInstance.RoomIndex` 注释写明「纯位置信息，不参与业务判定」 | 升级为业务真相（§5） |
| 一房一客 | `MoveVisitorToRoom` 只校验 `0..3`，**两个访客可同时在同一房间** | 加占用校验（§5.2） |
| 起居室 = 大堂不可分配 | 四间房平等，访客默认 `RoomIndex=0` | 房间 0 只作前台与通行（§5.1） |
| 接待后先分房再说需求 | `Accept` 直接 `FrontDesk → Serving` | 中间插入 `AwaitingRoom` 态（§5.3） |
| 服务中锁房 | 任何状态都可拖 | 按状态放行（§5.2） |
| 前台限 2 人排队、满房不投放 | 日程到点无条件 Spawn | 投放加前置条件（§5.4） |
| 交付 = 对话分支验收 | 交付页拖物品 + `Submit(ItemDef)` | 交付页整体退役（§6、§9） |
| 离场必留基础金钱 | 只有服务成功才给钱 | `Depart` 统一给（§8） |

**已经就位、不要重做的**（`ce0bd56` 四宫格提交）：四房间 2×2 连续世界与自由相机、访客拖拽换房的**表现层全套**（表现先行 → 业务裁决 → 被拒自动弹回）、每房间的 `visitorWalkArea`/`visitorEntryArea`（Excel 可配）、访客卡与名牌标注所在房间。本包**只补业务语义**，表现层改动量极小。

## 4. 数据结构规格

### 4.1 NeedDef 体系（新建 `Assets/Scripts/Visitor/NeedDef.cs` 等）

一条需求一个 SO 资产，多态用**抽象基类 + 子类**（与 `NodeDef`/`ResourceNodeDef` 同构，项目已有先例）：

```csharp
public enum ENeedType { None, Condition, Minigame }

public abstract class NeedDef : ScriptableObject
{
    [Tooltip("稳定键（日志/存档/编辑器索引用）")]
    public string needId;

    [TextArea]
    [Tooltip("需求描述：访客说出来的那句话，同时用于任务卡展示。对话里用 {需求} 占位符引用")]
    public string description;

    public abstract ENeedType NeedType { get; }
}

/// <summary>条件类：所住房间里存在下列家具中的**任意一件**即通过（OR 语义）。</summary>
public sealed class ConditionNeedDef : NeedDef
{
    public override ENeedType NeedType => ENeedType.Condition;

    [Tooltip("家具表（FurnitureTable）的行 id 列表；房间内存在任一即算满足")]
    public List<string> furnitureIds = new List<string>();
}

/// <summary>小游戏类：本包只建结构，小游戏本体与分档规则随小游戏框架定案（§7）。</summary>
public sealed class MinigameNeedDef : NeedDef
{
    public override ENeedType NeedType => ENeedType.Minigame;
    // 小游戏引用与分数→满意度的阈值配置，等小游戏框架定案后补（勿预设抽象，§15.3）
}
```

- 资产存放：`Assets/GameData/Needs/`，一条需求一个资产（与 `DialogueGroupDef` 同例：diff 友好、可拖拽引用、Unity 原生「查找引用」可用）。
- **家具 id 是字符串**（家具是 `FurnitureTable` 里的一行，不是独立资产），编辑器必须做成下拉选择，见 §4.5。
- **需求不挂专属对话**（访谈定案）：验收台词共用种族的 `ServiceCheck` 池，靠 `{需求}` 占位符把描述文本嵌进通用句式（如「你说的{需求}，我给你弄好了」）。将来要加是纯增量（加一个可空的对话组字段 + 回落），不预设结构（§16.6）。

### 4.2 日程表扩展（`VisitorScheduleTable`）

```csharp
public sealed class VisitorScheduleEntry
{
    public int day;
    public int appearMinute;
    public VisitorRaceDef race;
    public NamedVisitorDef namedOverride;   // 现状字段，仍未消费
    public NeedDef need;                    // ← 新增：本次拜访的需求（必填）
}
```

- **需求零随机**：谁在第几天几点带什么需求来，完全由策划配死。`VisitorManager.RollNeeds()` 整个删除。
- `need` 为空的日程条目：`LogError` 指名行号并**跳过投放**（没有需求的访客在新模型下无事可做）。
- Excel 导表侧（`访客日程表.xlsx` → `VisitorCsvImporter`）加一列「需求」，写 **NeedDef 的资产名**（与现有「对话池」列写 `Pool_fox` 同一做法）；解析失败打 Warning 不中断。**已知代价**：改资产名即断引用且无法「查找引用」，这是 Excel 引用 SO 的固有问题，接受。
- 现有告警仍然成立：**日程条目下标是派生种子的一部分，重排/插入既有行会改变对话抽取结果，加内容请追加在表尾。**

### 4.4 EVisitorState 新增一态

```csharp
public enum EVisitorState
{
    FrontDesk = 0,     // 前台等待接待：站在起居室入口区排队
    Serving = 1,       // 服务中：已入住某间客房，等需求被满足
    Wandering = 2,     // 闲逛：在自己房间里游走
    Departed = 3,      // 已离场
    AwaitingRoom = 4,  // ← 新增：已接待，等玩家把他拖进一间空客房
}
```

**枚举值必须显式赋值且新增只能追加**——存档接缝 `VisitorInstanceSaveData.state` 存的是 `(int)State`，改动已有值会静默错乱。

### 4.5 需求编辑器（新建 `Assets/Scripts/Visitor/Editor/NeedDefEditorWindow.cs`）

形态与 `DialogueEditorWindow` **同构，直接抄结构**：

```
┌─ 左树（可搜索）──────┬─ 右编辑区 ─────────────────┐
│ ▼ 条件类             │  用 Unity 默认 Inspector    │
│    需求_沙发         │  绘制选中的 NeedDef 本体     │
│    需求_茶具         │  （字段 UI 零重写）          │
│ ▼ 小游戏类           │                             │
│    需求_泡茶         ├─ 校验提示区 ────────────────┤
│ [+ 新建条件类需求]   │  ✗ 家具 id「xxx」不在家具表 │
└──────────────────────┴─────────────────────────────┘
```

- **左树按需求类型分两组**，带搜索框过滤（需求条数会随天数线性增长）；底部「新建」按钮分别创建两类资产。
- **右侧用默认 Inspector 绘制资产本体**——这是 `DialogueEditorWindow` 的关键取巧：字段 UI 一行不用写，属性抽屉自动复用。
- **家具 id 下拉做成 `PropertyDrawer`**（而不是写在窗口里）：这样窗口内与 Project 视图里直接选中资产两条路径都生效。下拉内容每次绘制从 `FurnitureTable` 重建（家具行数少，新导表立刻生效）；家具表缺失时退回手填文本框 + 警告，不阻塞编辑。
- 注册进**配置中心**（`ConfigHubWindow`，`MasterHouse → 配置中心` / `Ctrl+Shift+M`），与其他编辑器入口并列。
- **不做**：反向引用展示（"这条需求被第 3、7 天引用"）。日程表在 Excel 里存的是资产名字符串，反查只能扫 CSV 做字符串匹配，改名后还会误报孤儿——性价比不足，孤儿需求靠人工。

**校验规则**（分级参照 `DialogueAssetValidator`）：

| 级别 | 规则 |
|---|---|
| 报错 | `description` 为空；条件类的 `furnitureIds` 为空（永远无法满足）；`furnitureIds` 里的 id 不在家具表中（改名或删行导致） |
| 警告 | `needId` 与其他需求重复；同一 `furnitureIds` 里出现重复 id |

> ⚠ **执行时序陷阱**：唯一现成的「从家具表读 id 做下拉」实现在 `NodeSim/Editor/LevelDefEditorWindow.cs:463-506`，而**该文件会随 NodeSim 包一起删除**。若 NodeSim 包先执行，这段参考就没了——**要么本包先做，要么在删 NodeSim 前把那 40 行搬进新的 PropertyDrawer**。

## 5. 房间规则（本次改造的核心）

### 5.1 房间语义

| 房间 | 下标 | 语义 |
|---|---|---|
| 起居室 | 0 | **大堂**：大门所在地，访客到场在此入口区排队等接待。**不可分配为客房** |
| 卧室 / 厨房 / 书房 | 1 / 2 / 3 | 客房，可分配，**一房一客** |

在 `VisitorManager` 里定义常量（禁止散落魔数）：`LobbyRoomIndex = 0`、`FirstGuestRoomIndex = 1`、`LastGuestRoomIndex = 3`、`FrontDeskCapacity = 2`。

### 5.2 房间占用与拖拽裁决

```csharp
/// 房间是否已被占用：在场实例中有 Serving 或 Wandering 且 RoomIndex == 该房。
/// **闲逛也占房**——服务完成后访客仍在自己房间游走，直到离场才释放。
public bool IsRoomOccupied(int roomIndex)

/// 是否还有空客房（1~3 中至少一间未被占用）。接待分支的条件用它。
public bool HasFreeRoom { get; }
```

`MoveVisitorToRoom(instanceId, roomIndex)` 改为**按状态分派**，任一不满足返回 `false`（不抛异常，§8 契约），表现层的自动弹回机制会把演员送回原位：

| 访客状态 | 是否放行 | 行为 |
|---|---|---|
| `AwaitingRoom` | 目标 ∈ 1..3 且该房空闲 | **分配房间**：`RoomIndex` 更新 → 转 `Serving` → 请求【开始等待服务】对话（说出需求） |
| `Wandering` | 目标 ∈ 1..3 且该房空闲 | 换房，纯位置变更，无业务影响 |
| `FrontDesk` | **否** | 前台访客在门口排队，不可搬走 |
| `Serving` | **否** | **服务中锁房**——盲选房的赌注必须真实，否则条件类需求会退化成「把客人搬去已有那件家具的房间」 |

### 5.3 生命周期

```
日程到点 + 前台队列 < 2 + 有空客房
   │
   ▼
【前台等待接待】 站在起居室(0)入口区排队
   ├ 玩家点击 → 播【初次见面】对话（状态不变）
   │    ├ 分支选项「接待」（条件：HasFreeRoom，无空房则置灰）→ 转【等待分配房间】
   │    └ 分支选项「拒绝」 → 按拒绝口径结算离场
   └ 等搭话超时 → 按拒绝口径结算离场
   │
   ▼
【等待分配房间】 仍在起居室入口区，任务卡提示「把客人拖进一间空房」
   ├ 玩家拖到空客房松手 → 转【服务中】+ 播【开始等待服务】对话（**此时才说出需求**）
   └ 拒绝仍然可用（打烊清场需要）
   │
   ▼
【服务中】 已入住，房间被占
   ├ 条件类：玩家去弄家具 → 点访客 → 播【服务中交谈】对话
   │            └ 分支选项（条件：RoomHasAnyFurniture）满足才可选 → 结算事件 → 判「完美」
   ├ 小游戏类：点访客 → 播【服务中交谈】对话 → 分支选项「开始」→ 启动小游戏（本包占位）
   └ 等交货超时 → 按拒绝口径结算离场
   │
   ▼
【闲逛】 在自己房间游走冒泡，房间仍被占
   ├ 累计达种族上限 → 离场
   └ 打烊时按种族概率 roll 跨天留宿
   │
   ▼
离场 → **留下基础金钱**（§8）→ 房间释放
```

**「先盲选房、进房后才说需求」是硬要求**：【初次见面】对话只负责打招呼与接待/拒绝，绝不能提前透露需求内容。

### 5.4 投放规则

`SpawnDueVisitors()` 的投放前置条件改为：**前台在场人数 < 2** 且 **至少有一间空客房**。

- 条件不满足时**日程游标不前进**，卡在那一条上等待——玩家一腾出前台/房间，下一位立刻进场。
- 因此日程表里的「出现时刻」语义退化为「**最早**出现时刻」，文档与导表说明需同步这句。
- 【待确认】当天打烊时仍未投放的日程条目：**默认作废并打一条 Warning**（不顺延到次日，避免滚雪球）。

## 6. 条件类需求的完整闭环

### 6.1 房间家具查询（新建，`Assets/Scripts/Furniture/FurniturePlacementQuery.cs`）

**不要让业务层直接读 `FurnitureRoomController.sessions`**——那是 View 层的 static 字典（§11.4）。新建一个只读查询封装：

```csharp
public static class FurniturePlacementQuery
{
    /// 该房间当前摆放的全部家具 id（含地面/壁挂/桌面家具）。
    public static IReadOnlyList<string> FurnitureIdsIn(int roomIndex);

    /// 该房间是否摆放了列表中的任意一件（OR 语义；列表为空返回 false）。
    public static bool RoomHasAny(int roomIndex, IReadOnlyList<string> furnitureIds);
}
```

实现要点（**这三条是踩过的坑，务必照做**）：

1. 数据来源是 `FurnitureRoomController.CaptureSessionPlacements(roomId)`，**返回 null 表示「该房间从未编辑过」，必须回落到 `room.initialPlacements`**——忘了回落就会漏判初始摆放的家具。`FurnitureSceneComposer.Collect` 里的 `?? room.initialPlacements` 就是这个回落，照抄。
2. 桌面家具（`hostFurnitureId` 非空）与地面/壁挂家具混在同一个列表里，**两者都要算**——客人不关心杯子放在地上还是茶几上。
3. `roomIndex` → `roomId` 的换算走 `FurnitureRoomTable.rooms[roomIndex].id`，越界返回空。

### 6.2 新增对话条件与事件

在 `Dialogue/GameplayConditions.cs` / `GameplayActions.cs` 里追加（普通 `[Serializable] class`，不受「独占同名文件」约束）：

| 类型 | 名称 | 语义 |
|---|---|---|
| 条件 | `RoomHasAnyFurnitureCondition` | 【访客/所住房间有需求家具】读 `ctx.Visitor.Need` 转 `ConditionNeedDef`，调 `FurniturePlacementQuery.RoomHasAny(ctx.Visitor.RoomIndex, need.furnitureIds)`。**不是条件类需求时返回 false** |
| 条件 | `HasFreeRoomCondition` | 【访客/还有空客房】挂在【初次见面】的「接待」选项上，满房时该选项自动置灰 |
| 事件 | `CompleteNeedAction` | 【访客/完成需求结算】调 `VisitorManager.CompleteNeed(instanceId, EServeSatisfaction.Perfect)`。属奖励类事件，**只允许放在对话组末尾或分支选项上**（对话说明 §5.3 铁律 2） |
| 事件 | `StartMinigameAction` | 【访客/开始小游戏】本包占位：`LogWarning` + Toast「小游戏尚未接入」。**不要为它预建抽象**（§7） |

`AcceptVisitorAction` 语义修改：由「进入服务中」改为「进入等待分配房间」，`SubclassLabel` 文案同步改。

**类改名必须挂 `[MovedFrom]`**，否则策划已配的对话数据会被静默清空——这是本项目唯一的高危操作。

### 6.3 结算与满意度

新增业务方法，取代被删除的 `Submit`：

```csharp
/// 完成需求结算：记账 → 请求【完成服务】对话 → 转闲逛（或不对味时直接离场）。
/// 条件类固定传 Perfect；小游戏类由小游戏框架按分数定档（§7）。
public bool CompleteNeed(int instanceId, EServeSatisfaction satisfaction)
```

- 内部逻辑照抄现有 `Submit` 的后半段（`CompleteGuestService` 记账 → `Data.Today` 累计 → 请求 `ServiceDone` 对话 → `Mismatch` 直接离场、其余转 `Wandering`），**只去掉扣库存与 `Evaluate` 两步**。
- **条件类固定判「完美」**（用户定案）。四档枚举 `EServeSatisfaction` 与四个【完成服务·档位】对话组**全部保留不动**——小游戏类要用。
- `Evaluate` / `Preview` / `EconomyConfig.SatisfactionThresholdPercent`（阈值 A）随 tag 评分一起删除。

### 6.4 「服务中交谈」触发分类

现有八个对话分类里没有「服务中再次交谈」——`serviceStart` 是「刚进屋说出需求」，语义不同，每次点击都重播完整需求对话体验很差。

**默认实现**：`EVisitorDialogueTrigger` 新增 `ServiceCheck`，`DialoguePoolDef` 加一个 `serviceCheck` 列表字段，校验器与编辑器窗口同步补。验收分支挂在这一类的对话组上。

`HubPage.SelectGuest` 的 `case EVisitorState.Serving:` 由「打开交付页」改为「请求 `ServiceCheck` 对话」；新增 `case EVisitorState.AwaitingRoom:` 给一条 Toast 提示拖拽分房。

## 7. 小游戏类需求（本包只占位）

小游戏框架尚未设计（另开专题），本包**只做到结构就位**：

- `MinigameNeedDef` 建类、可配 `description`，其余字段留空。
- `StartMinigameAction` 执行时 `LogWarning` + Toast 提示未接入，**不改变任何业务状态**。
- 小游戏类需求的访客因此只能走「拒绝」或「等交货超时」离场——这是**明示的过渡态**，验收时不算 bug。
- **不要**为小游戏预建接口、注册表、Def 基类或任何抽象（§15.3「不预设抽象、不建没有调用方的接缝」）。

已达成的小游戏共识（供下一包参考，本包不实现）：UGUI 页面而非 GameObject；唯一入口是需求调起、唯一出口是一个分数；与其他模块零耦合；期间关营业闸门；无限重开、退出即重置，因此无需存档。

## 8. 经济改动

| 改动 | 说明 |
|---|---|
| **离场必留基础金钱** | 所有业务访客离场时都留下一笔基础货币——**包括被拒绝与超时流失的**。这是新模型下「不会陷入没钱死循环」的保证 |
| **未满足需求不扣钱** | 只是拿不到额外奖励 |
| 满足需求的奖励 | 沿用 `EconomyManager.CompleteGuestService(satisfaction)` 按档发放 |

落点：`VisitorManager.Depart(instance)` 里统一调用。氛围邻居（ambient）不在 `Data.Instances` 里，天然不受影响。

【待确认】基础金额的配置位置与数值：**默认实现**为 `EconomyConfig` 新增全局单值 `guestLeaveTip`（暂定与现有单次服务奖励同量级），留注释标本项；策划实测后若需按种族差异化，再迁到 `VisitorRaceDef`。

【待确认】拒绝与两段超时是否仍扣声望：**默认保留现状两档惩罚**（`refuseReputationPenalty` / `serviceFailedReputationPenalty`），留注释标本项。
