## 1. New Game 开场播片 ✅（HouseUI）

**决策**（2026-08-22）：

- 素材形态：**视频文件（mp4/webm）**，用 Unity VideoPlayer 播（`com.unity.modules.video` 已默认启用；Windows 下 H.264 mp4 兼容性最稳）。
- 跳过：**点击任意处/任意键立即跳过**整段。
- 流程位置：New Game 点击 → **播片（可跳）→ 现有 OpeningZoomFx 开场推镜 → Hub**。播片负责叙事，推镜负责"落地到房子"的空间感，两者都保留。

**现状与接缝**：全仓目前 0 处 VideoPlayer 引用、0 个视频资产——这是全新能力。接入点是 `TitlePage.StartNewGame()`（重置各 Manager 之后、`OpeningZoomFx.Play` 之前插一个播片页/叠加层）。

**限制与注意**：

- ⚠ **视频素材待美术提供**（分辨率、时长未定）；素材到位前可先落框架（黑屏占位）。
- 不做"看过就不再播"（无持久化）；每次 New Game 都播，靠点击跳过兜底。
- 视频音量与设置项（house-settings.json 音量体系）的对接可后续再收，第一版直出。

## 2. 小游戏开局教程图遮罩 ✅（Minigame）

**决策**（2026-08-22）：

- 粒度：**每个小游戏一张图**，配在 `MinigameDef` 上（新增 Sprite 字段，留空则不弹）。
- 频次：**本次运行内、同一小游戏仅首次进入时弹**（静态内存标记，不持久化，重启游戏会再弹）。
- 关闭：点击任意处关闭；建议 ESC 在遮罩期间也等价于关闭遮罩（而不是中止小游戏）。

**现状与接缝**：小游戏目前没有任何"开始前的门"——`MinigameOverlay.Open` 实例化完立即 `Launch`，玩家直接落进可操作局面。落点在宿主 `MinigameOverlay`：Instantiate 之后、`Launch` 之前盖全屏遮罩，关闭后才 `Launch`（遮罩期间游戏未开始、不吃输入不走时间）。

**限制与注意**：教程图美术素材待提供（电路、咖啡各一张）；遮罩实现放宿主层，不违反"小游戏不认识业务侧"的依赖硬约束。

## 4. 待客室同时只允许一位等待访客 ✅（Visitor）

**决策**（2026-08-22）：**接待室总人数 ≤ 1**——`VisitorManager.FrontDeskCapacity` 常量 2 → 1，计数口径不变（前台未接待 + 已接待待分房两态合计）。门口同时最多站一人；上一位分完房，下一位才进场。

**现状**：`FrontDeskCapacity` 是代码常量、不在任何配置资产里；投放闸门在 `SpawnDueVisitors`——满员时日程游标不前进（"出现时刻"本就是"最早出现时刻"语义），跨天未投放的条目作废并 Warning。

**限制与注意**：

- ⚠ 上限减半后**日程更容易憋单**：排得密的日程会整体后移、跨天条目更容易作废。策划排日程表时需按"单通道"节奏留间隔。
- 需求 #8（接待后强制立即分房）会把"待分房"停留时间压到很短，可部分抵消憋单。

## 5. 气泡统一「···」+ 删黄色感叹号 + 闲聊冒泡显示台词 ✅（Visitor + Dialogue）

**决策**（2026-08-22）：气泡拆成**两种语义**：

1. **可交互提示 = 「···」气泡图**（美术资源已有）：当"此刻点他有对话"（现有 `NoTalkReason == None` 判据：前台队首可接待／服务中已示意／待告别）时**常驻显示**；取代黄色感叹号——代码画的黄底「！」标记（`BuildAttentionMarker` 及脉动逻辑）整体删除。
2. **闲聊冒泡 = 显示台词文字**：保留现有间歇节奏（4~10 秒随机，`VisitorTuningConfig` 调参），但把从闲聊池（`EDialogueCategory.SmallTalk`，带 recent 去重）抽到的那句台词**真正显示在气泡里**——现状是管线已抽到文本但表现层丢弃、只显示一张无字贴图。
3. 规则：可交互状态下只显示常驻「···」，**不再叠**闲聊文字冒泡，避免两种语义打架。

**现状与接缝**：气泡表现在 `OutGameVisitorBubble`（贴图路径/尺寸目前是代码常量）；台词请求链 `VisitorManager → DialogueManager.RequestBubble → OutGameVisitorStage → actor.ShowBubble` 已通，只差表现层画字。

**限制与注意**：

- ⚠ 闲聊**文字气泡需要一张可拉伸底板**（九宫格 + 文本区）——美术项，与「···」图是两个素材。
- 闲聊文字的实际覆盖取决于对话表闲聊池的填充情况（内容填表是另一条在途待办）。
- 1.0 访客卡上的「！」角标已随 2.0 主页面退役、当前不显示，不另处理；若回滚 1.0 版式需同步删除。

## 6. 左上角时间只显示小时 ✅（HouseClock + HouseUI）

**决策**（2026-08-22）：格式**暂按「14时」**（中文后缀）处理；⚠ 最终格式标注**后续继续对**（美术/团队）。

**现状与接缝**：2.0 时间牌走字在 `HubChromeBinder`，读共享的 `HouseClockData.TimeText`（`HH:MM`）。**不要直接改 `TimeText`**——日历面板、1.0 顶栏等还有 3 个消费方。做法：`HouseClockData` 新增小时格式属性（如 `HourText`），仅时间牌消费，其余不动。

## 7. NPC 点击区域扩大到气泡+立绘 ✅（Visitor 表现层）

**决策**（2026-08-22）：**仅气泡显示时扩大**——气泡对象自身挂 Raycast 并把点击转发给演员（与立绘同一点击入口）；气泡隐藏时热区回到立绘（现状：演员根上透明 Image，大小 = 整张序列帧包围盒）。

**限制与注意**：气泡可见期间其热区会吃掉背后一小块房间点击/相机平移起手，属预期代价；拖拽移除（#8）后演员的点击/拖拽仲裁（`Dragging` 吞点击）可一并简化。

## 8. 分房改点击：接待后强制分配模式 ✅（Visitor + HouseUI）

**决策**（2026-08-22）：

- 【初次见面】对话末尾选「接待」→ 对话层收起后**立即进入分配模式**：可分配的空客房高亮，**点击空房即完成分配**（业务走现有 `MoveVisitorToRoom`，裁决逻辑不变）。
- **完成分配前不可退出该模式**：ESC、点其他访客、开面板、结束今天等交互全部挡住；**相机操作（滚轮/平移/点房聚焦）保持可用**，玩家需要能看各房间。
- **拖拽全链路移除**：舞台层拖拽事件链（BeginDrag/Drag/EndDrag、边缘推屏、弹回）、演员四个拖拽方法、`HubPage.OnVisitorDropped` 整链退役。

**安全性**：现状业务里无空房时「接待」选项本就点不出来（`CanAcceptGuest = 有空房 && 无待分房`），所以进入分配模式时必有空房，不会死锁；待分房本就是唯一阻塞【结束今天】的状态，口径一致。

**限制与注意**：

- ⚠ **连带后果：闲逛访客换房能力取消**（原先玩家可把闲逛客拖去别的空房）。如后续需要换房，另做点击方案，本轮不做。
- 点房间的语义仲裁：分配模式中点空房 = 分配；其余情况点房 = 聚焦推镜（现状不变）。
- 落地后 `Docs/四宫格房间与访客拖拽说明.md` 的拖拽章节需标注退役。

## 9. 滚轮优化 ✅（HouseUI · Hub 相机）

**决策**（2026-08-22）：**保持连续缩放手感，加档位边界卡点**：

- 一/二（外景↔总览）、二/三（总览↔聚焦）档边界处加阻尼卡点：滚到边界停住，**再滚一次才过界**。
- **二→三过界时自动吸附**：推镜到**悬停高亮框所指房间**的标准取景（复用现成 `FocusRoom` / `FocusZoom`，0.55s 推镜）。
- **新增房间悬停高亮框**：总览态下鼠标所在房间显示高亮框（示意"继续放大会进这间"）。目前不存在，需新做（现成积木：指针→视口→`HubWorldGrid.RoomAt`→`RegionOf` 画框，框建在世界根下随相机零换算）。
- **整体调低滚轮灵敏度**：现系数 0.16/格，下调（具体值为调参项）。
- 三档内继续上滚放大看细节（至 6×）照旧。

**限制与注意**：卡点边界要与现有"重影带禁停"逻辑（GhostBand / LodBand 的 snap）协调，避免卡点恰好落在禁停带内——实现时定。

## 10. 两件可直入小游戏的家具 ⏸（Furniture + Minigame，暂缓）

**状态**（2026-08-22）：**整条暂缓，需进一步讨论后再排期。**

访谈中的初步方向（仅作讨论记录，不构成决策）：机制走家具族新增「小游戏入口」配置字段；先用现有家具占位、加入初始摆放，美术到位后只换资产行。

**待讨论的未决点**（也是暂缓的原因）：

- 进入的**关卡怎么选**（点名关卡／关卡池抽取／选关 UI）。
- **无访客上下文的结算出口**：`MinigameOverlay.HandleFinish` 目前写死回调 `VisitorManager.CompleteNeed`，家具入口需要一条"无访客"分支。
- **入口消化点**：`ConsumePending` 目前只在对话结束时被调用，家具点击进入需另找消化点（或当场开页）。

**现状**：全仓没有任何"家具→功能"机制（Hub 场上点家具现在无操作，家具详情入口已注释停用）；归档设计里"家具→小游戏"曾被明确列入不做栏，不是预留好的接缝。

## 11. 对话赠送家具 ✅（Dialogue + Economy）

**确认结论**：**现在不能**。对话事件字典只有 8 个函数（Accept/Reject/Leave/CompleteNeed/StartMinigame/AddCurrency/AddReputation/Log），没有给家具的动作；经济侧也没有公开的无偿授予接口（唯一授予是开局初始携带用的私有函数）。

**决策**（2026-08-22）：**本轮实现** `GrantFurniture(家具id[,数量])` 对话动作。要动四处：

1. `DialogueFuncs.Actions` 加一行，**标 `isReward: true`**（否则 ESC 中断对话后可重复领取）。
2. `EconomyManager` 新开公共的无偿授予家具接口。
3. ⚠ `Tools/导表/make_dialogue_template.py` 的 `ACTIONS` 硬编码清单**必须同步加**——漏改则策划 Excel 的动作下拉里没有这项。
4. 导表校验（`DialogueCsvImporter`）对着 Actions 字典自动生效，无需手改。

**限制与注意**：获得反馈第一版用 Toast（「获得×家具名」）；商店的"获得物品弹窗"深绑在商店页 Prefab 内，本轮不拆出来复用。

## 12. 需求对话：可交付时仅显示交付选项 ✅（Dialogue）

**决策**（2026-08-22）：**运行时规则、零改表**——对话业务层加一条固定规则：分支里存在「条件含 `RoomHasNeedFurniture` 且当前满足」的选项时，**仅显示这些选项，其余选项整个隐藏**（不是置灰）。现有 10+ 个需求对话组零改表即时生效，未来新组也不用配。

**现状与接缝**：

- 选项条件现有语义是「不满足 → 置灰保留可见」（本身还是设计 §12 的待确认默认值，本条不改它，只在其上叠一条"独占"规则）。
- 求值链：`DialogueManager.CurrentOptions` / `IsOptionEnabled`（条件纯查询、可反复求值）→ `DialogueOverlay` 渲染三态。落地时需引入"可见选项"概念，注意：选项下标映射（`ChooseOption` 按原始下标）、键盘导航、2.0 选项列自下而上占格布局（隐藏后槽位自然收缩）。

**限制与注意**：

- 规则以 `RoomHasNeedFurniture` **条件函数**为键，天然只作用于条件类（家具）需求对话；小游戏类需求（`StartMinigame`）不受影响。若未来交付选项改用别的条件写法，需同步这条规则。
- 校验器「每个分支至少一个无条件选项」的防卡死硬规则不受影响、不用改：交付条件不满足时其余选项照常可见。
