## 1. 一句话目标

把「同款家具的不同换色」从**隐式的 id 命名约定**扶正为**显式的家具族**，并让族吸收全部族级共有属性——策划改一处、整族生效；需求可以按族配；商城与收纳栏按族折叠。

## 2. 现状与动机

### 2.1 族已经存在，但是隐式的

- 家具表现有 **121 行**，id 命名规整：`<族名>_<两位编号>`（`single_sofa_02`、`cat_sofa_01`、`table_lamp_06`…）。
- `StoreOverlay.FamilyKey(id)`（`:244`）= 取最后一个 `_` 之前的部分；`FamilyName(displayName)` = 显示名去掉 `·NN` 后缀。商城的色块选择就是这么聚合出来的。
- **靠命名猜族**的问题：哪天有个 id 不守规矩（如只有单件的 `armchair_01`）就会静默出错，而且无法表达"这两件长得像但不同族"。

### 2.2 族级属性在 121 行里大量重复（实测）

`single_sofa` 族 11 行的字段对比：

| 列 | 11 行的实际值 |
|---|---|
| 分类 / 表面类型 / 占格列 / 占格行 / 显示宽 / 装饰分 | **完全相同**（桌椅 / 地面 / 3 / 2 / 185 / 32） |
| 显示高 | 194~201，**逐个微调过**（按素材实测） |

改一次「单人沙发占几格」要手改 11 行，漏一行就是隐性 bug。这是族表最大的价值，比解决需求匹配大得多。

### 2.3 三个受影响的场景

| 场景 | 现状痛点 |
|---|---|
| **配置需求** | 条件类需求按 `furnitureId` 精确匹配 → 需求写蓝椅子、玩家买了红椅子就**判定不通过且不知道为什么** |
| **摆放（收纳栏）** | `FurnitureRoomHud.EntriesOf(surface)` 逐条平铺 121 件再翻页，绝大多数是换色 |
| **购买（商城）** | 已按族聚合，但靠 id 前缀猜 |

## 3. 族表设计

### 3.1 载体

新建 `Excel/家具族表.xlsx` → `Assets/Configs/家具族表.csv` → `FurnitureFamilyTable.asset`（`Resources/OutGameUI/`），走与家具表完全相同的导表管线（导表工具说明 §8「新增一类配置表的步骤」照抄）。

### 3.2 字段划分（按真实归属，**不做覆写机制**）

划分依据是 §2.2 的实测：同族必然相同的进族表，逐变体不同的留家具表。

**族表（11 列 + 族标识）**

```
族id            稳定键，家具行引用它
族显示名        「单人沙发」（商城卡片标题、收纳栏槽位名）
分类            商店页签
描述            商店详情文案
表面类型         可多选（地面/桌面/壁挂）
可叠放
占格列 / 占格行
装饰分
拿起音效 / 放下音效
桌面格启用 + 5 个参数
```

**家具表（保留变体特有 + 新增族引用）**

```
id / 英文索引 / 显示名（带 ·NN）/ 显示宽 / 显示高 / 精灵图 / 色值
族id            ← 新增列
```

> **为什么显示宽也留在变体行**：实测里它当前恰好同族相同（185），但它与显示高是一对，拆开会让策划困惑——显示高确实需要逐个微调。**不引入「族默认值 + 变体覆写」**，那会违反项目既定的「每个数值只有一个家」原则（访客交付说明 §4.3）。

### 3.3 关键技巧：导表时展开，运行时结构不变

**`FurnitureEntry` 一个字段都不删。** 导表时由导入器把族属性**展开填进每一行** `FurnitureEntry`：

```
家具族表.csv ─┐
              ├─→ FurnitureCsvImporter ─→ FurnitureTable.asset（121 行，每行字段齐全）
家具表.csv  ─┘        （逐行按族id查族表，把 11 个族级字段填进去）
```

收益：**商城 / 摆放 / 烘焙 / 装饰分 / 需求匹配等全部消费方零改动**。SO 里有数据冗余，但那是机器生成的产物，不是策划的负担。

实现要点：

- **导入顺序有依赖**：必须先读族表再读家具表。`CsvPostprocessor` 若同时收到两个 CSV 的变化，要保证族表先解析。
- 家具行引用了不存在的族 id → **`LogError` 指名行号并跳过该行**（不静默用默认值，否则会得到一件占格 1×1 的沙发，极难查）。
- 族表里没有任何成员的族 → `LogWarning`（可能是刚建还没配家具，不阻塞）。
- `FurnitureEntry` 新增一个 `familyId` 字段（这是唯一的结构新增），供商城/收纳栏/需求匹配按族分组。

## 4. 三个场景的改动

### 4.1 购买（商城）—— 极小

`StoreOverlay.BuildFamilies` 里：

- `FamilyKey(entry.id)` → `entry.familyId`
- `FamilyName(entry.displayName)` → 族表的族显示名
- `FamilyKey` / `FamilyName` 两个私有方法**删除**（隐式约定退役）
- `FlatCategories`（盆栽等平铺不聚合的特例）：有了显式族之后可以**统一按族聚合**——一族只有一件的自然就渲染成一张单卡。落地时确认能否直接删掉这个特例。

### 4.2 配置需求 —— 小

`ConditionNeedDef` 新增：

```csharp
[Tooltip("按族匹配：房间里有该族的任意配色即算满足")]
public List<string> familyIds = new List<string>();
```

- 与现有 `furnitureIds` 是 **OR 关系**：任一命中即满足。
- 两者并存的理由：族满足「随便什么颜色的单人沙发都行」，精确 id 满足「就要那张蓝的」。
- `FurniturePlacementQuery` 增加对应重载：`RoomHasAnyFamily(roomIndex, familyIds)`。
- 需求编辑器：家具下拉旁增加**族下拉**；两个列表都显示每项的**解禁声望与售价**（策划才能看出「这条需求得玩家有 40 声望才做得了」）。

### 4.3 摆放（收纳栏）—— 本次大头

一族一个槽位，条目数从 121 降到约 20~30，**一页基本看完，翻页痛点自然消解**。

- **槽位内嵌色块条**，与商城的交互形态保持一致（玩家学一次就会）：点色块切当前配色，从槽位拖出即摆放。
- 收纳栏**只列已拥有的配色**（未拥有的不显示——购买一律走商店，见 `FurnitureRoomHud.cs:143` 现有注释）。
- **余量数字标在色块上**，余量按**具体 id** 计算而不是按族（摆出去的是那一件具体的东西）。余量口径见装饰分文档 §4.2/§4.5。
- 【待确认】一族配色过多（十几个）时色块条放不下：**默认**横向滚动；若手感差再改成换行。
- 族内全部配色余量都为 0 时，整个族槽位置灰。

### 4.4 不受影响的

**装饰分、可摆余量、购买所有权一律按具体 id 计**，不按族。族只是**分组与配置的单位**，不是所有权的单位。

## 5. 校验规则

| 级别 | 规则 |
|---|---|
| 报错 | 家具行的族 id 不存在于族表；族 id 重复；族表必填列为空 |
| 警告 | 族没有任何成员；同族成员的表面类型/占格在展开后仍不一致（说明族划错了） |
